# Шаг 01 / спринт 42: пробная проверка решения без траты попытки

**Дата:** 2026-11-05  
**Спринт:** 42 (v0.5.0 «Learning Experience & Teaching Workflow»)  
**Задача:** S42-001 — пробная проверка решения без траты попытки  
**Статус:** реализовано

---

## 1. Что сделано

1. **Новый эндпоинт `POST /tasks/{id}/check`.** Прогоняет тест-кейсы задачи
   в песочнице и возвращает тот же разбор, что и `submit`, но **не меняет**
   счётчик попыток и статус задачи, **не создаёт** запись прогресса и **не
   начисляет** достижения. В ответе `SubmitResponse.practice = true` — по
   нему интерфейс отличает пробу от отправки.
2. **Сервис без дублирования логики.** `TaskService.check_solution()`
   использует общие с `submit_solution()` раннер `_run_cases()` (запуск
   тест-кейсов) и сборщик сообщения `_build_message()`. Разница двух
   методов — только учёт прогресса.
3. **Лимит на пользователя.** `CHECK_LIMIT = 20` пробных проверок в минуту
   (`app/core/rate_limiter.py`: `is_user_limited`), fail-open — как и
   остальные лимиты проекта. При превышении — 429 с `Retry-After: 60`.
   Лимит по пользователю, а не по IP: один ученик не должен выжигать
   ресурсы песочницы, а за общим IP сидит весь класс.
4. **Интерфейс.** На странице задачи рядом с кнопкой отправки — кнопка
   «Пробная проверка» и подсказка «не засчитывается в попытки». Результат
   пробы показывается отдельной карточкой («Результат пробной проверки»),
   рядом с результатом отправки.
5. **Побочные правки, найденные по ходу:**
   - Кнопка отправки была подписана «Проверить решение», хотя
     `docs/USER_GUIDE.md` уже называл её «Отправить решение». После
     появления пробной проверки две кнопки «Проверить…» путались —
     переименовано в «Отправить решение» (ui + e2e + документация).
   - Сторы вынесены в отдельный чанк сборки: рост состояния стора задач
     (`checkResult`, `checking`) поднял entry-бандл до 80.13 kB gzip —
     выше зафиксированного в `docs/ARCHITECTURE.md` предела 80 kB. После
     выноса чанка `stores` entry — 69.51 kB gzip.

  окружения `KI-017`, новых проблем не заводил.
- **Полный `pytest` в образе и e2e на CI** будут прогнаны коммитом спринта;
  локально проверены целевые наборы (задачи, контракт) и полный e2e.

  `docs/USER_GUIDE.md` — это синхронизация UI с документацией, а не
  самостоятельная правка.

## 5. Обоснование решений

| Вариант | Выбран | Почему |
|---------|--------|--------|
| Отдельный эндпоинт vs флаг в `submit` | **Отдельный эндпоинт** | Разная семантика (учёт прогресса) — её нельзя выразить флагом в теле без риска, что клиент «забыет» флаг и случайно спишет попытку. Разный контракт виден в OpenAPI и в UI. |
| Лимит по IP vs по пользователю | **По пользователю** | Общий IP у всего класса: лимит по IP блокировал бы урок целиком. Ограничение ресурса песочницы — per-user. |
| Fail-open или fail-closed при недоступном Redis | **Fail-open** | Как и остальные лимиты проекта (`RULES.md` §11): защита не должна ронять API. Песочница всё равно ограничена собственным `executor_max_concurrency`. |
| Отдельный тип ответа vs флаг `practice` | **Флаг в `SubmitResponse`** | Флаг — аддитивное изменение контракта (не ломает клиентов), а второй тип ответа заставил бы дублировать схему и валидацию. |
| Переименовать кнопку отправки | **Да** | Две кнопки «Проверить…» рядом — источник ошибок; `docs/USER_GUIDE.md` уже использовал «Отправить решение». |
| Сторы отдельным чанком vs сократить код | **Отдельный чанк** | Рост состояния стора в спринте 42 продолжится (черновик, история попыток) — вынос в чанк снимает вопрос сразу; правка кода лечила бы симптом. |

## 6. Что дальше

Следующий шаг спринта 42 — **S42-002 «История попыток»**: таблица
`task_attempts` (код, результаты по кейсам, время), эндпоинт
`GET /tasks/{id}/attempts` и блок истории на странице задачи. Он опирается
на общий раннер `_run_cases()`, уже выделенный в S42-001.

Пробная проверка станет первым источником этих записей: если S42-002
реализует историю только для засчитанных отправок, проба в неё не попадёт
(попытка не засчитана) — это осознанное поведение, а не пропуск.
