# Шаг 04 / спринт 42: поиск и фильтры каталога

**Дата:** 2026-11-05  
**Спринт:** 42 (v0.5.0 «Learning Experience & Teaching Workflow»)  
**Задача:** S42-004 — поиск и фильтры в UI каталога  
**Статус:** реализовано

---

## 1. Что сделано

1. **Фильтр по статусу на сервере.** `GET /tasks?status=not_started|in_progress|completed`
   отбирает задачи по прогрессу **того ученика**, который сделал запрос
   (LEFT JOIN по `user_task_progress`). Без записи прогресса задача считается
   «не начата». Ключ кэша списка задач учитывает статус — иначе выдача у
   разных учеников по одному фильтру смешалась бы.
2. **Поиск и фильтры в интерфейсе.** Строка поиска (по названию и описанию),
   фильтры категории (список из `GET /tasks/categories`), тега и статуса,
   счётчик найденного, кнопка «Сбросить фильтры», отдельное пустое
   состояние с подсказкой (без фильтров — прежний текст).
3. **Состояние в URL.** Фильтры читаются из query-параметров при открытии
   страницы и пишутся в них при изменении — ссылкой можно поделиться.
4. **Задержка ввода и отмена запросов.** Поиск отправляется через 300 мс после
   остановки набора; предыдущий запрос каталога отменяется через
   `AbortController`, поэтому поздний ответ не подменяет свежий.

## 4. Проблемы и отклонения

- **Локальный venv отстаёт от `requirements.txt`** (fastapi 0.115.5 против
  0.162.0) — контрактные тесты OpenAPI падают на нём и без этих правок.
  Полный прогон backend выполнен в образе с зафиксированными зависимостями
  (`ai-teacher-backend:step42d`, Python 3.12.16). Известный риск окружения
  `KI-017`, новых проблем не заводил.
- **Тест фильтра по тегу падал из-за отсутствия тегов в фикстуре.** В
  `tests/test_tasks.py` локальный `TASK_PAYLOAD` не содержит `tags` (в отличие
  от `tests/task_helpers.py`), поэтому задача создавалась без тегов и фильтр
  `?tag=basics` ничего не возвращал. Добавлен отдельный хелпер
  `_create_task_with_tags` — общий `TASK_PAYLOAD` не менялся, чтобы не
  затронуть другие тесты.
- **Нумерация разделов `docs/USER_GUIDE.md` сдвинулась** на единицу из-за
  нового раздела «Поиск и фильтры» (§6). Перенумерованы последующие
  разделы и подразделы, внутренняя ссылка «§8.3» исправлена на «§9.3».
  Внешних ссылок на сдвинутые разделы в других документах нет.

## 5. Обоснование решений

| Вариант | Выбран | Почему |
|---------|--------|--------|
| Фильтр по статусу на сервере или в браузере | **На сервере** | Статус зависит от прогресса конкретного ученика — в браузере пришлось бы фильтровать уже загруженную страницу, а она ограничена `limit=100`. На сервере фильтр точен и попадает в кэш. |
| Фильтр по статусу как отдельная колонка в `tasks` | **Через LEFT JOIN прогресса** | Статус — свойство пары «ученик + задача», а не задачи. Дублировать его в `tasks` означало бы хранить состояние, зависящее от пользователя, в общей таблице. |
| Состояние фильтров в URL или в сторе | **В URL** | Ссылкой можно поделиться с учеником или коллегой — для учебного сценария это полезнее, чем скрытое состояние. Стор при этом остаётся источником для запроса. |
| Отмена устаревших запросов | **AbortController** | Без отмены поздний ответ по старому фильтру подменял бы результат свежего — список «мигал» бы при быстром наборе. |
| Задержка ввода поиска | **300 мс** | Запрос на каждый символ перегружал бы API. 300 мс — компромисс между задержкой ввода и числом запросов. |
| Пагинация каталога | **Не в этом шаге** | Фильтры сужают выдачу, но пагинация (`skip`/`limit` в API есть, кнопки «ещё» — нет) — отдельная работа; она не входила в S42-004. |
