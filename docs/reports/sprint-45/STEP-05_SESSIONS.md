## 1. Что сделано

1. **Таблица `user_sessions`.** Миграция `019`: `id`, `user_id` (CASCADE),
   `jti` (уникальный), `user_agent`, `ip`, `created_at`, `last_used_at`,
   `revoked_at`, индекс по `user_id`. Модель `UserSession` в `models/user.py`.
2. **`jti` в паре токенов.** `issue_token_pair(user, jti=...)` кладёт
   идентификатор сессии в access и refresh. Login создаёт строку сессии и
   передаёт `jti`; refresh проверяет строку, ротирует `jti` и обновляет
   `last_used_at` — старый refresh-токен становится одноразовым.
3. **Совместимость деплоя.** Refresh-токены без `jti` (выданные до шага) не
   отклоняются: для них создаётся новая сессия. Активные пользователи не
   разлогиниваются при обновлении.
4. **`GET /users/me/sessions`.** Действующие сессии пользователя с UA, IP,
   временем входа/активности; текущая определяется по `jti` access-токена и
   помечается `current: true`.
5. **`DELETE /users/me/sessions/{id}`.** Точечный отзыв: `revoked_at`,
   следующий refresh устройства — 401. Чужая/несуществующая — 404, текущая —
   400 (для неё есть выход). Аудит `user.session_revoked`.
6. **«Выйти на всех устройствах».** `POST /users/me/sessions/revoke-others`
   увеличивает `token_version`, отзывает все строки и создаёт новую сессию
   для текущего устройства, возвращая новую пару. Аудит
   `user.sessions_revoked` с числом отозванных.
7. **Смена пароля.** Также отзывает строки сессий и создаёт новую для
   текущего устройства (согласовано с S45-001).
8. **UI.** Карточка «Активные сессии»: устройство, время входа/активности,
   IP, метка «Это устройство», кнопка «Отозвать» для остальных, кнопка
   «Выйти на всех устройствах» с подтверждением.
9. **Тесты.** Backend — 11: создание сессии при входе, две сессии, отзыв
   чужой сессии и мёртвый refresh, запрет отзыва текущей и чужой, ротация
   `jti`, старый токен без `jti`, «выйти везде» (обе старые сессии мертвы,
   новая жива), рост `token_version`, аудит, требование авторизации.
   Frontend — 5: список и метка текущей, отзыв с перезагрузкой, ошибка
   загрузки, «выйти везде» с сохранением новой пары, отмена.

## 4. Проблемы и отклонения

- **Ротация ломает «текущность» старого access-токена.** После refresh строка
  сессии получает новый `jti`, поэтому access-токен из прежней пары перестаёт
  помечаться как текущий. Это корректно: фронтенд сохраняет новую пару сразу;
  e2e-тест проверяет список до ротации.
- **Отзыв текущей сессии запрещён (400).** Иначе клиент остался бы без пары
  токенов и без внятного UX; для выхода есть кнопка «Выйти».
- **`user_sessions` не чистится retention-планировщиком.** Отозванные строки
  невелики и нужны для аудита; при необходимости их можно удалять вместе с
  истёкшими refresh-токенами — отдельная задача.
- **Гонка refresh.** Два одновременных refresh с одним токеном: второй
  получит 401, потому что `jti` уже ротирован. Это ожидаемое поведение
  одноразового токена.

## 5. Обоснование решений

| Вариант | Выбран | Почему |
|---------|--------|--------|
| Список сессий из refresh-токенов без БД | **Таблица `user_sessions`** | Нужны UA/IP, отзыв и «текущая» метка; JWT сам это не хранит. |
| `sid` (id строки) вместо `jti` | **`jti`** | Соответствует формулировке задачи; уникальность и ротация удобны. |
| Отзыв через `token_version` на каждую сессию | **Точечный `revoked_at`** | Версия — грубый рубильник; точечный отзыв не трогает остальные устройства. |
| «Выйти везде» с потерей текущей сессии | **Новая пара текущему** | KI-028 требует, чтобы текущее устройство осталось. |
| Отклонять старые токены без `jti` | **Принимать один раз** | Иначе деплой разлогинил бы всех. |
