## 3. Почему стало быстрее

1. **Батчинг (S23-001).** Раньше каждый тест-кейс — отдельный интерпретатор:
   ~0.5–0.6 с на кейс, 3 кейса ≈1.8 с. Теперь один процесс на задачу,
   построчный JSON-протокол, таймаут **на кейс** (зависший кейс убивает
   процесс, остальные помечаются `SandboxError`). Экономия — 2 старта из 3.
2. **Пул тёплых интерпретаторов (S23-002).** Старт процесса (импорт
   RestrictedPython + приложения) — ~0.3 с; пул убирает его из горячего пути:
   p50 упал с 358 до 35 мс. Процесс переиспользуется, но:
   - на каждую задачу/кейс — свежие `globals`/`builtins` (`_run_restricted`);
   - после `TimeoutError`, `MemoryError` и сбоя протокола процесс убивается;
   - после `EXECUTOR_POOL_MAX_TASKS` (50) — плановый перезапуск;
   - при shutdown приложения (`lifespan`) пул закрывается.

## 5. Ограничения и риски

1. **Стенд — одна машина.** Цифры зависят от CPU; на слабее VM knee ниже.
   Цель 5 RPS достигнута с запасом, поэтому запас есть.
2. **Лимит памяти ставится один раз на процесс пула.** Это компромисс:
   RLIMIT_AS/Job Object нельзя ослабить или навесить дважды. Практически
   лимит задаётся конфигом и одинаков для всех задач.
3. **p99 ≈ 338 мс** в сценарии submit — это «холодные» первые запросы, пока
   пул поднимает процессы; после прогрева p99 стабилизируется.
4. **Конкурентность клиента 5** ограничивает измерение: 15 RPS без пула дали
   12.5 фактических. Для честного knee нужен отдельный прогон с большей
   конкурентностью (не требуется для бюджета этапа).

## 6. Воспроизведение

```powershell
# backend с пулом (или EXECUTOR_POOL_SIZE=0 — сравнение с батчем)
$env:DEBUG='false'; $env:LLM_PROVIDER='echo'; $env:RATE_LIMIT_ENABLED='false'
$env:SEED_ON_START='true'; $env:EXECUTOR_POOL_SIZE='2'
.\venv\Scripts\uvicorn.exe app.main:app --host 127.0.0.1 --port 8000

# гейт: 5 RPS, p95 ≤ 2000 мс, exit 1 при нарушении бюджета
python scripts/load_test.py --scenario submit --rps 5 --duration 20 `
    --json-out ..\docs\reports\sprint-23\load-test.json
```
