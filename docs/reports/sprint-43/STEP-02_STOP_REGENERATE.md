**Дата:** 2026-11-05  
**Спринт:** 43 (v0.5.0 «Learning Experience & Teaching Workflow»)  
**Задача:** S43-002 — остановка и регенерация  
**Статус:** реализовано

---

## 1. Что сделано

1. **Команда остановки в протоколе чата.** Клиент шлёт `{"type":"stop"}`,
   сервер прерывает поток на ближайшей дельте, сохраняет полученный текст как
   ответ ассистента с пометкой `message_metadata.stopped = true` и отвечает
   `{"type":"stopped","content":"<частичный текст>"}`. Соединение не
   закрывается: после остановки можно писать дальше.
2. **Генерация вынесена в отдельную задачу.** Раньше цикл сокета ждал
   завершения стрима и не мог прочитать `stop`. Теперь стрим идёт в фоновой
   задаче, а цикл принимает сообщения (`ping`, `stop`, `chat`). Параллельная
   генерация в одном соединении отклоняется ошибкой.
3. **Частичный ответ сохраняется и при разрыве соединения.** Если клиент
   закрыл сокет во время генерации, сервер фиксирует полученный текст с тем
   же признаком `stopped` — диалог не теряется.
4. **Ответ сохраняет вызывающий, а не генератор.** `ChatService.stream_reply`
   больше не пишет ответ в БД: его сохраняет WebSocket-слой (`save_reply`).
   Так частичный ответ фиксируется даже тогда, когда генератор прерван.
5. **Регенерация ответа.** `POST /chat/sessions/{id}/messages/{message_id}/regenerate`
   просит ассистента ответить на тот же вопрос заново, с тем же уровнем
   помощи. Вопрос ученика не дублируется, прежний ответ не попадает в
   контекст LLM.
6. **Пометки в метаданных.** Прежний ответ остаётся в истории с
   `replaced = true` и `replaced_by = <id нового ответа>`; остановленный
   ответ — с `stopped = true`. Новых таблиц и миграций не понадобилось.
7. **Интерфейс.** Кнопка «Стоп» в шапке диалога вместо индикатора
   стриминга, кнопка «Повторить» под каждым ответом ассистента, пометка
   «Ответ остановлен» в переписке. Новый ответ занимает место прежнего —
   диалог не разрастается.
8. **Детерминированный порядок сообщений.** В relationship
   `ChatSession.messages` добавлен `order_by` по `created_at`: без него
   PostgreSQL отдавал строки в физическом порядке, и порядок сообщений в API
   зависел от того, как вставлены строки.

## 4. Проблемы и отклонения

- **Команда `stop` вместо разрыва соединения.** Требование допускало и
  «закрыть/отменить соединение». Разрыв выбран как аварийный сценарий:
  клиент теряет уведомление о сохранённом частичном ответе. Основной
  механизм — команда `stop`: сервер подтверждает остановку событием
  `stopped`, соединение остаётся живым. Разрыв тоже обрабатывается — ответ
  сохраняется.
- **Понадобилась переработка цикла сокета.** Пока стрим выполняется внутри
  цикла чтения, команда `stop` не может быть прочитана. Стрим вынесен в
  отдельную задачу; из-за этого `ping` теперь отвечается сразу, не дожидаясь
  конца генерации, — порядок сообщений в двух старых тестах обновлён.
- **Ответ сохраняет не генератор, а вызывающий.** Иначе при прерывании
  генератора (обрыв сокета) код после `yield` не выполнялся и ответ не
  попадал в БД. Теперь сохранение ответственность WebSocket-слоя.
- **Порядок сообщений в API был недетерминированным.** Relationship
  `ChatSession.messages` не имел `order_by`, и ответы API приходили в
  физическом порядке строк. Это проявилось как падение теста S42-006 после
  добавления `commit`/`refresh` в сервисе. Исправлено `order_by` по
  `created_at` — поведение API теперь гарантировано.
- **Остановка в REST-режиме не поддерживается.** Без WebSocket ответ
  приходит целиком и останавливать нечего; кнопка «Стоп» показывается
  только во время стриминга.
- **E2E-сценарий остановки не написан:** провайдер `echo` отвечает мгновенно,
  остановить поток в тесте невозможно. Остановка покрыта unit-тестами
  сервера и клиента.
- **Первый полный e2e-прогон дал одно падение** в `tasks.spec.ts`
  («верное решение засчитывается») — прогон шёл одновременно с полным
  backend-прогоном, и песочница не успела отработать за 60 с. Повторный
  прогон без параллельной нагрузки: **25 passed, 1 skipped**. К изменениям
  S43-002 падение отношения не имеет.

## 5. Обоснование решений

| Вариант | Выбран | Почему |
|---------|--------|--------|
| Останавливать разрывом соединения или командой | **Командой `stop`** (разрыв — аварийный случай) | Клиент получает подтверждение и может продолжить разговор в том же сокете; при разрыве уведомления нет. |
| Отменять задачу стрима или проверять флаг между дельтами | **Флагом между дельтами** | Проверка флага не трогает генератор провайдера: отмена задачи внутри `async for` оставила бы «висящее» HTTP-соединение. Остановка срабатывает на ближайшей дельте. |
| Кто сохраняет ответ ассистента | **Вызывающий (WebSocket-слой)** | Генератор может быть прерван до конца — тогда его код сохранения не выполнится. |
| Хранить признак остановки и замены | **В `message_metadata`** | Без новой таблицы и миграции; данные нужны только для интерфейса и аудита. |
| Удалять прежний ответ при регенерации | **Оставлять с пометкой `replaced`** | История остаётся честной: видно, что ответ меняли и какой. |
| Дублировать вопрос при регенерации | **Не дублировать** | Диалог не должен разрастаться; LLM получает тот же контекст, что и в первый раз. |
| Новый ответ — в конец истории или на место старого | **На место старого в интерфейсе** | Ученик видит привычную переписку; в БД оба ответа остаются с временными метками. |
| Останавливать генерацию по HTTP-запросу | **Только по сокету** | REST-ответ приходит целиком, отдельный маршрут остановки был бы лишней сущностью. |

агрегатами для администратора), S43-004 (экспорт диалога в Markdown/JSON и

считаться полноценным ответом при сборе метрик.
