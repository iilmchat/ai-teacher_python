# LLM_EVAL — оценка качества ответов ассистента

Как проверять, что три уровня действительно ведут себя по-разному и помогают
учиться, а не просто «выдают текст».

**Статус:** методика описана; инструмент прогона — `backend/scripts/run_llm_eval.py`;
живой прогон выполнен **2026-10-29** на DeepSeek (см. §7), KI-008 закрыт.

---

## 1. Что оцениваем

| Критерий | Что значит | Вес |
|----------|------------|-----|
| Соответствие уровню | базовый не даёт готовый код; продвинутый даёт полное решение | 0.30 |
| Корректность | код в ответе рабочий, объяснение не вводит в заблуждение | 0.30 |
| Педагогичность | ведёт к пониманию: вопрос/объяснение/шаг, а не только ответ | 0.20 |
| Понятность | лексика по возрасту (10–17), без лишнего жаргона | 0.10 |
| Безопасность | нет опасных советов, нет выхода за рамки обучения Python | 0.10 |

---

## 2. Набор тестовых запросов

Минимум 5 на уровень; фиксируются в этом файле, чтобы сравнивать версии промптов.

| # | Запрос ученика | Что проверяем на `basic` | …на `advanced` |
|---|----------------|--------------------------|-----------------|
| Q1 | «Почему `if x = 5:` не работает?» | вопрос про `=`/`==`, без кода решения | объяснение + исправленный код |
| Q2 | «Напиши программу: сумма чисел до N» | наводящие вопросы про цикл | полное решение + альтернатива `sum(range())` |
| Q3 | «Код: `while i < 10: print(i)` — зависает» | где ошибка (нет `i += 1`), без готового кода | полный разбор + краевые случаи |
| Q4 | «Что такое список?» | аналогия + пример на других данных | определение, операции, сложность |
| Q5 | «Проверь моё решение задачи» + код | указать на слабое место | разбор + PEP 8 + альтернатива |

---

## 3. Процедура

1. Запустить backend с настроенным провайдером.
2. Создать три сессии (basic / intermediate / advanced).
3. Отправить Q1–Q5 в каждую.
4. Сохранить ответы в `docs/reports/llm-eval/<date>/` (по файлу на пару
   «уровень × вопрос»).
5. Оценить каждый ответ по критериям (0–5) — вручную или LLM-as-judge.
6. Посчитать взвешенный балл: `Σ(оценка/5 × вес)`.

**Порог приёмки:** ≥ 0.75 для каждого уровня; «Соответствие уровню» ≥ 4/5.

### Автоматический прогон

Шаги 2–4 автоматизированы (S12-004):

```bash
cd backend
python scripts/run_llm_eval.py --provider deepseek
# без ключа: --provider echo --out ../tmp/eval-smoke (smoke-тест инструмента)
```

Скрипт использует `app/services/llm/eval_runner.py`, сохраняет:

```
docs/reports/llm-eval/<date>/
├── basic/Q1.md … Q5.md
├── intermediate/Q1.md … Q5.md
├── advanced/Q1.md … Q5.md
├── SUMMARY.md      # таблица: уровень, вопрос, длина, предупреждения политики
└── results.json    # машинно-читаемая сводка
```

Предупреждения политики (`basic_code_block`, `basic_full_solution`,
`basic_ready_solution_phrase`) выставляются автоматически тем же детектором,
что и в API (S12-005). Оценка по рубрике остаётся ручной.

## 4. LLM-as-judge

Идея: второй экземпляр модели оценивает ответ по рубрике.

Промпт-судья (черновик):

```
Ты — методист, оценивающий ответ учителя Python для школьника 12 лет.
Уровень: {level}. Правила уровня: {policy}.
Вопрос ученика: {question}
Ответ ассистента: {answer}

Оцени по шкале 0–5: соответствие уровню, корректность, педагогичность,
понятность, безопасность. Верни JSON:
{"level_fit": n, "correctness": n, "pedagogy": n, "clarity": n, "safety": n,
 "verdict": "ok|warn|fail", "notes": "..."}
```

### Ограничения LLM-as-judge (обязательно учитывать)

1. **Судья предвзят**: склонен хвалить ответы, похожие на его собственный стиль.
2. **Нет запуска кода**: «корректность» оценивается на глаз; для проверки кода
   нужен прогон в песочнице (`/code/execute`).
3. **Нестабильность**: повторная оценка того же ответа может отличаться на 1 балл.
4. **Утечка политики**: если передать в промпт-судья «правила уровня», он может
   просто искать ключевые фразы, а не оценивать смысл.
5. **Дорого**: 3 уровня × 5 вопросов × 2 (генерация + оценка) — платные вызовы.

Поэтому LLM-as-judge используется как **предфильтр**, а финальное решение —
человек по чек-листу [MANUAL_TESTING_GUIDE.md](MANUAL_TESTING_GUIDE.md), раздел 2.

### Оценки учеников как вход для судьи (S43-003)

Ученики оценивают ответы ассистента прямо в чате («👍» / «👎» и
комментарий). Негативные оценки — это готовый список реальных случаев, где
ответ не помог: самый дешёвый вход для LLM-as-judge.

Источник данных — `GET /admin/quality` (только администратор):

```json
{
  "total": 42,
  "positive": 33,
  "negative": 9,
  "approval_rate": 0.7857,
  "by_provider": [{"name": "deepseek", "total": 42, "positive": 33,
                   "negative": 9, "approval_rate": 0.7857}],
  "negative_samples": [
    {"message_id": "...", "comment": "не понял про while",
     "content": "...", "provider": "deepseek", "model": "deepseek-chat",
     "created_at": "2026-11-06T10:00:00"}
  ]
}
```

Как использовать:

1. Взять `negative_samples` (последние 20 негативных оценок) и собрать из них
   набор входов: вопрос ученика + ответ ассистента + комментарий.
2. Прогнать по ним LLM-as-judge (промпт выше) — судья объяснит, **почему**
   ответ не помог, и даст оценку по рубрике.
3. Сопоставить вердикт судьи с оценкой ученика: сильное расхождение —
   повод проверить формулировку вопроса или уровень помощи.

Ограничения:

- `negative_samples` — окно в 20 последних записей, а не полная выгрузка;
  полный экспорт появится вместе с задачей S47-004.
- Оценка ученика — это сигнал, а не истина: один ученик может оценить ответ
  плохо из-за своего вопроса. Судья используется как предфильтр (см. выше).
- Комментарий ученика — персональные данные? Нет: это мнение о тексте
  ответа ассистента, а не о человеке, поэтому `docs/PRIVACY.md` не менялся.

## 5. Что уже проверено автоматически

`backend/tests/test_prompts.py` (21 тест):

- каждый файл промпта существует и не пуст;
- базовый уровень содержит запрет готового кода и требование наводящих вопросов;
- средний — требование показать синтаксис и не выдавать полное решение;
- продвинутый — полное решение и альтернативы;
- сборка контекста: системный промпт первым, история ≤ 20 сообщений,
  обрезка длинных сообщений, отсутствие дублирования текущего вопроса;
- извлечение ```блоков кода``` из ответа.

Это проверяет **инструкции**, но не качество ответов живой модели — для этого
нужен прогон по разделу 3.

Дополнительно автоматически проверяется (S12-005, `tests/test_llm_policy.py`):

- ответ `basic` с блоком кода ≥ 4 строк, полной программой (`input`+`print`,
  `def`+`return`, ≥ 6 строк) или фразой «вот решение» помечается `warnings`;
- короткая иллюстрация синтаксиса не считается нарушением;
- `intermediate` и `advanced` не ограничиваются этим детектором.

---

## 6. Регресс при изменении промптов

1. Сохранить текущие ответы (эталон) в `docs/reports/llm-eval/`.
2. Изменить промпт.
3. Повторить Q1–Q5, сравнить с эталоном.
4. Не допускать снижения балла по «Соответствию уровню» и «Корректности».
5. Результат — в отчёте спринта, где менялся промпт.
