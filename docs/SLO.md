# SLO.md — целевые уровни сервиса (S35-006)

> Этап: v0.6.0 «Production Hardening». Документ задаёт **базовые** SLO для
> закрытого пилота на одном узле. Multi-node и HA в этап не входят, поэтому
> доступность ограничена одним VPS и ручным восстановлением (см. §7).
>
> Владелец SLO: владелец продукта. Технический владелец: backend-разработчик
> (алерты и метрики). Пересмотр — раз в квартал и после каждого инцидента.

---

## 1. Окно и метод

- **Окно:** календарный месяц (30 дней), time-based SLI.
- **Источник:** Prometheus, scrape `/metrics` каждые 15 с
  (`deploy/monitoring/prometheus/prometheus.yml`).
- **Исключения:** плановые окна обслуживания (деплой/миграции) до 30 минут в
  месяц, согласованные заранее; всплески, вызванные внешним LLM-провайдером,
  не снимают ответственность с продукта, но учитываются отдельным SLO (§4).
- **Расчёт:** `1 - (плохие события / все события)` по PromQL из §2.

---

## 2. Базовые SLO

| # | SLI | SLO | PromQL (30 дней) |
|---|-----|-----|------------------|
| 1 | Доступность API | **≥ 99.0%** успешных запросов (не 5xx) | `1 - (sum(rate(http_requests_total{status=~"5.."}[30d])) / clamp_min(sum(rate(http_requests_total[30d])), 0.001))` |
| 2 | Доля ошибок | **< 1.0%** 5xx от всех HTTP-запросов | `sum(rate(http_requests_total{status=~"5.."}[30d])) / clamp_min(sum(rate(http_requests_total[30d])), 0.001)` |
| 3 | Latency health | **p95 `/health/ready` < 100 мс** | `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{path="/health/ready"}[30d])) by (le))` |
| 4 | Latency API | **p95 ≤ 500 мс** (кроме стриминга/песочницы) | `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{path!~"/api/v1/chat/.*"}[30d])) by (le))` |
| 5 | Latency submit | **p95 ≤ 2 с** для `POST /tasks/{id}/submit` | `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{path="/api/v1/tasks/{task_id}/submit"}[30d])) by (le))` |
| 6 | Успешность LLM | **≥ 99%** вызовов без `status="error"` | `1 - (sum(rate(llm_requests_total{status="error"}[30d])) / clamp_min(sum(rate(llm_requests_total[30d])), 0.001))` |

> Health p95 < 100 мс — самый строгий SLI: он отражает не только процесс, но и
> доступность БД/Redis (readiness делает `SELECT 1` и `PING`).

## 3. Error budget

Для доступности 99% в окне 30 дней:

```
бюджет ошибок = 1% × 30 дней = 0.01 × 43 200 мин ≈ 432 мин ≈ 7 ч 12 мин
```

Правила расходования:

| Сожжено | Действие |
|---------|----------|
| < 50% | обычный темп; инциденты разбираются в рабочем порядке |
| 50–75% | заморозка рискованных изменений в auth/edge и песочнице; ревью инцидентов |
| 75–100% | только фиксы и стабилизация; новый функционал — после восстановления бюджета |
| > 100% | постмортем, план восстановления, пересмотр SLO или архитектуры |

Аналогично для ошибок (<1%) и LLM (≥99%).

## 4. Алерты, связанные с SLO

Правила лежат в `deploy/monitoring/prometheus/rules/alerts.yml`; описание
действий — `docs/MONITORING.md` (якоря `runbook_url`).

| Алерт | Что означает для SLO |
|-------|----------------------|
| `High5xxRate` | быстрый расход бюджета доступности/ошибок |
| `ApiLatencyHigh` | риск нарушения SLO #4 |
| `BackendDown` | полная недоступность, бюджет сгорает со скоростью 100% |
| `DatabaseDown`, `RedisDown` | деградация health и API, риск SLO #1–#4 |
| `LLMErrorRateHigh`, `LLMSlowResponses`, `LLMFallbackSpike` | риск SLO #6 |
| `SandboxTimeoutsSpike` | риск SLO #5 и пользовательской деградации |
| `RateLimitSpike` | возможный абуз/брутфорс, косвенно влияет на доступность |
| `RetentionStale`, `BackupStale` | операционные SLO (данные и восстановление) |

**Burn-rate (рекомендация).** Для пилота достаточно пороговых алертов выше. При
переходе на полноценный SRE-режим добавить multi-window burn-rate:

```promql
# 1h burn rate > 14.4 (2% бюджета за час) и 5m > 14.4
job:http_errors_5xx:ratio5m / 0.01 > 14.4
```

## 5. Как считать вручную

Prometheus UI (`http://127.0.0.1:9090`) → Graph → запросы из §2 с шагом `1h`.
Для месяца удобнее `increase(...[30d])`. Grafana-дашборд
`AI Teacher — Overview` показывает текущие значения (5xx ratio, latency p95),
но не считает бюджет за 30 дней — это делает запрос.

Проверка метрик после деплоя:

```bash
python scripts/monitoring/check_metrics.py \
  --url http://127.0.0.1:8000/metrics --expect-workers 2
```

## 6. Вне SLO

- доступность внешнего LLM-провайдера (DeepSeek/LM Studio) — отдельный
  контракт провайдера; продукт отвечает за fallback и корректную деградацию;
- задержки браузера/сети пользователя;
- плановые окна обслуживания и восстановление после DR-учений;
- корректность учебного контента (это качество продукта, см. `LLM_EVAL.md`).

## 7. Ограничения одного узла

Пилот работает на одном VPS: падение узла = недоступность до восстановления
(ручной рестарт/restore), поэтому 99% — реалистичный, а не «пять девяток»
таргет. Multi-node/HA вынесены за границы v0.6.0 (TODO_V0.4.md §9). При
переходе на несколько реплик SLO пересматриваются (доступность ≥ 99.5%,
latency без изменений).
