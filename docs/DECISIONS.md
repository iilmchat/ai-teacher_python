## 1. D-001 · Стратегия релиза: v0.5.0 раньше v0.4.0

**Решение:** следующим продуктовым релизом выпускается **v0.5.0**
(спринты 47 → 48). Незавершённые задачи v0.4.0 не отменяются и не
растворяются в спринте 48: они остаются отдельным бэклогом
«Production Hardening» в `TODO_V0.4.md` и должны быть закрыты до
production-эксплуатации в режиме multi-node/HA.

**Почему:**

- 42–46 уже построены поверх текущей платформы; 47–48 не зависят от 34–41.
- Пользовательская ценность v0.5.0 (обучение, чат, песочница, аккаунт,
  кабинет учителя) уже готова; остановка на 2–3 недели ради v0.4.0
  откладывает её без технической необходимости.
- Смешивать 34–41 и 48 в один спринт нельзя: релиз перестанет быть
  управляемым (см. отклонённый вариант 3).

**Отклонённые варианты:**

| Вариант | Почему отклонён |
|---------|-----------------|
| Сначала полностью закрыть v0.4.0 (34–41), потом 47–48 | Сдвиг v0.5.0 минимум на 2–3 недели; зависимости от 34–41 у 47–48 нет |
| Слить остатки v0.4.0 в спринт 48 | Взрывной рост scope релиза, высокий риск сорвать и релиз, и hardening |

**Границы и компенсирующие меры:**

1. v0.5.0 позиционируется как **single-node** релиз. В release notes и
   `RELEASES.md` явно указывается: multi-node, HA, DR и SLO 2.0 — не входят.
2. `KI-023` (merge-gate не обеспечен на GitHub Free) остаётся открытым;
   зелёные проверки продолжают запускаться, но не являются технически
   обязательными. Это известное ограничение, а не скрытый дефект.
3. В `TODO_V0.4.md` добавляется баннер «отложено, не блокирует v0.5.0».
4. Перед любым production-развёртыванием (не demo/single-node) задачи
   34–41 должны быть закрыты отдельным этапом.

**Следствие для спринта 48:** релиз v0.5.0 не требует закрытия `KI-023`,
но требует честной фиксации ограничений в документации.

## 2. D-002 · Комментарий модератора — отдельная колонка

**Решение:** в `tasks` добавляется nullable-колонка
`moderation_comment` (`Text`). Комментарий пишется при действии «Вернуть в
доработку», виден автору задачи в кабинете учителя и сохраняется до
следующей публикации. История всех комментариев остаётся в `audit_log`
(`task.moderated`), в колонке — только актуальный.

**Почему:** колонка даёт автору быстрый доступ к причине возврата без
разбора журнала; аудит остаётся источником истории. Отдельная таблица
комментариев избыточна для одного актуального сообщения.

## 3. D-003 · «Проблемные темы» — по категории/тегам задачи

**Решение:** «топ проблемных тем» в сводке качества считается по
`tasks.category` и `tasks.tags` для задач, к которым привязан чат.

**Правило привязки:** у сообщения ученика в `message_metadata.task_context`
есть `task_id` (S42-006). Негативная оценка ответа относится к задаче,
если в сессии есть сообщение с `task_context.task_id`; при нескольких
задачах в одной сессии берётся **последний** контекст перед оцениваемым
ответом. Если контекста нет — запись попадает в группу «без задачи» и не
искажает топ.

**Почему:** категории и теги — существующая таксономия задач, не требуют
LLM-классификации и остаются стабильными между прогонами.

## 4. D-004 · Деактивация пользователя — `is_active=false`

**Решение:** администратор деактивирует пользователя мягко:
`is_active=false`. Это отдельное действие от жёсткого `DELETE`.

Правила:

- `PATCH /admin/users/{id}` принимает `is_active`;
- при деактивации отзываются все `user_sessions` и увеличивается
  `token_version` (пользователь выходит на всех устройствах);
- повторная активация возвращает доступ, но не старые сессии;
- нельзя деактивировать себя;
- жёсткое удаление (`DELETE`) остаётся отдельной необратимой операцией и в
  UI подписывается явно («Удалить безвозвратно»);
- аудит: `user.deactivated`, `user.activated`; жёсткое удаление —
  существующий `user.deleted`.

**Почему:** деактивация — обратимый административный сценарий; жёсткое
удаление не должно быть единственным способом «выключить» аккаунт.

## 5. D-005 · Массовые действия с пользователями — атомарный bulk-эндпоинт

**Решение:** `PATCH /admin/users/bulk` с телом:

```json
{
  "user_ids": ["uuid", "..."],
  "changes": {"role": "teacher", "is_active": false}
}
```

- лимит — 100 пользователей за запрос;
- сначала валидация всего набора, затем применение **одной транзакцией**;
- в `skipped` попадают: несуществующие id, сам администратор, попытка
  снять роль с администратора, объекты без изменений;
- `updated` — id, к которым изменения применены;
- одно аудит-событие `user.bulk_updated` со сводкой (роль, флаг, количества);
- если после валидации `updated` пуст — 200 с пустым списком, без ошибки.

**Почему:** один запрос вместо N `PATCH`; одна транзакция исключает
частично применённое состояние; отчёт `updated/skipped` объясняет, что
именно произошло, не превращая частичный пропуск в 4xx.

## 6. D-006 · CSV журнала аудита — отдельный потоковый эндпоинт

**Решение:** `GET /admin/audit/export` с теми же фильтрами, что у
`GET /admin/audit` (`action`, `entity_type`, `actor_id`, `search`),
формат CSV (UTF-8 BOM), потоковая отдача, лимит `EXPORT_MAX_ROWS`, аудит
`audit.exported`.

**Почему:** `export_service` предназначен для аналитических наборов
(`users|tasks|attempts|activity`) с фиксированными колонками; журнал аудита
имеет свой набор полей и фильтров. Отдельный эндпоинт не ломает контракт
выгрузки и переиспользует общий streaming-подход.

## 7. D-007 · Ссылки из уведомлений — серверный `link` + клиентский fallback

**Решение (best practice):**

1. Новые уведомления получают в payload поле `link` — относительный путь
   внутри приложения (например, `/tasks/{task_id}`,
   `/classrooms/{classroom_id}`, `/assignments`). Ссылку формирует сервер,
   клиент не собирает маршрут из произвольных полей.
2. Для `assignment` и `deadline` в payload добавляется `task_id` (сейчас
   его нет) — он нужен и для ссылки, и для будущих переходов.
3. Клиент принимает только внутренние пути: `link` должен начинаться с
   `/` и не содержать `//` и схем (`http:`, `javascript:`); иначе ссылка
   игнорируется. Это защита от open redirect/XSS через payload.
4. Для уведомлений, созданных до изменения, `link` может отсутствовать —
   клиент использует fallback по известным полям:
   `attempt_feedback → /tasks/{task_id}`,
   `announcement → /classrooms/{classroom_id}`,
   `assignment/deadline → /assignments`.
5. `link` не заменяет идентификаторы: payload остаётся машиночитаемым.

**Почему:** сервер знает актуальные маршруты и права; клиентский fallback
обеспечивает обратную совместимость без миграции старых уведомлений.

## 8. D-008 · Выгрузка негативных оценок — отдельный эндпоинт

**Решение:** `GET /admin/quality/export?format=csv|json` — потоковая
выгрузка негативных оценок с комментариями, провайдером, моделью, уровнем
и привязкой к задаче (если есть). Аудит `quality.exported`, лимит
`EXPORT_MAX_ROWS`.

**Почему:** это не аналитический набор из `export_service`, а вход для
`docs/LLM_EVAL.md`; отдельный эндпоинт сохраняет стабильные колонки и не
смешивает ПДн с агрегатами.
