## Активные проблемы

### KI-001 · Open · Med · docker, config, docs · перейти на канонические порты, когда освободятся

**Описание:** Канонические порты проекта заняты контейнерами других проектов на этой машине:
`5432` — `ticket-postgres`, `6379` — `workflow-builder-redis`. Из-за этого наши контейнеры
не могли опубликовать порты, а подключение молча уходило в чужую БД и падало с
`password authentication failed for user "ai_teacher"`.

**Workaround:** проект использует `5434` (Postgres) и `6381` (Redis). Внешние порты
параметризованы через `POSTGRES_PORT` / `REDIS_PORT` в `.env` и `docker-compose.yml`,
поэтому смена порта — только правка ENV, без изменения кода.
Чужие контейнеры не останавливались (RULES §11.2).

**План закрытия:** вернуть `5432`/`6379` в `.env.example` и `docker-compose.yml`
по умолчанию, когда порты освободятся; проверить `docker compose up` и тесты.

**Создано:** 2026-10-29 · **Обновлено:** 2026-10-29

### KI-002 · Open · Low · docs, ci · автоматическая проверка расхождения моделей и миграций

**Описание:** Тестовая схема создаётся через `Base.metadata.create_all`, а рабочая — через
Alembic. Расхождение между ними не ловится тестами: именно так прошёл баг с enum
(KI-004) — тесты были зелёными, а реальный сервер отвечал 500.

**Workaround:** проверка `alembic check` добавлена в чек-лист RULES §10 и в CI.

**План закрытия:** добавить интеграционный тест, который применяет миграции к пустой БД
и сравнивает схему с `Base.metadata` (`alembic check` как pytest-тест).

**Создано:** 2026-10-29 · **Обновлено:** 2026-10-29

### KI-006 · Open · Low · api/websocket, tests · интеграционный тест стриминга

**Описание:** WebSocket-стриминг проверен только на отказе авторизации.
Полный сценарий (start → token… → done, сохранение ответа в БД) не покрыт
автотестом: `TestClient` живёт в отдельном event loop, а WS-эндпоинт создаёт
собственную сессию БД, поэтому не изолируется существующей транзакционной
фикстурой.

**Workaround:** логика чата покрыта на уровне `ChatService` и `test_chat.py`
(там используется `generate`, а не `stream`).

**План закрытия:** вынести получение сессии и пользователя в FastAPI-зависимости
WS-эндпоинта, чтобы подменять их в тестах; добавить тест полного стриминга.

**Создано:** 2026-10-29 · **Обновлено:** 2026-10-29

### KI-007 · Open · Med · core/rate_limiter, main · middleware не подключён

**Описание:** `create_rate_limit_middleware` реализован и использует
`redis.asyncio`, но не зарегистрирован в приложении: нужен Redis-клиент,
создаваемый в `lifespan`. Сейчас лимиты фактически не применяются.

**Workaround:** лимиты описаны в RULES §7.2 как требование; до подключения
middleware вход не ограничивается.

**План закрытия:** создать `app/db/redis.py`, открывать клиент в `lifespan`,
добавить `add_middleware` и тест на 429 после 5 попыток логина.

### KI-008 · Open · Med · services/llm, QA · нет проверки реальных ответов LLM

**Описание:** Провайдеры DeepSeek и LM Studio покрыты тестами только на уровне
фабрики: реальные вызовы не выполнялись, потому что нет API-ключа DeepSeek и
не запущен LM Studio. Качество и «дисциплина» ответов по уровням (базовый не
должен давать готовый код) на живой модели не проверены.

**Workaround:** промпты проверены на наличие обязательных маркеров
(`test_prompts.py`), маршрутизация уровней — интеграционными тестами с
фейковым провайдером.

**План закрытия:** добавить `LLM_PROVIDER` с ключом в `.env`, прогнать
`docs/MANUAL_TESTING_GUIDE` для 3 уровней, зафиксировать примеры ответов и
оценки в `docs/reports/`.

### KI-009 · Open · Med · core/executor · лимит памяти не enforced

**Описание:** `EXECUTOR_MEMORY_LIMIT=128` МБ хранится в настройках, но не
применяется: модуль `resource` недоступен на Windows, а `subprocess` не умеет
ограничивать RSS кроссплатформенно. Код, выделяющий много памяти
(`[0] * 10**9`), может нагрузить машину до срабатывания таймаута.

**Workaround:** жёсткий таймаут 5 секунд убивает процесс; запуск идёт в
отдельном интерпретаторе, поэтому падение не роняет API.

**План закрытия:** на Linux/Docker добавить `resource.setrlimit(RLIMIT_AS)` в
раннере; для Windows — `Job Objects` через `pywin32` или вынести исполнение в
отдельный контейнер с `--memory=128m`.

**Создано:** 2026-10-29 · **Обновлено:** 2026-10-29

### KI-010 · Open · Low · db/seed · задачи наполняются вручную

**Описание:** Учебные задачи добавляются скриптом `backend/scripts/seed_tasks.py`,
который нужно запускать отдельно. В Docker-развёртывании и CI задачи не
появляются автоматически, поэтому `/api/v1/tasks` на чистой базе пуст.

**Workaround:** запуск `python scripts/seed_tasks.py` после миграций
(см. GETTING_STARTED).

**План закрытия:** добавить data-миграцию или команду `make seed`,
вызываемую в entrypoint контейнера при `SEED_ON_START=true`.

## Закрытые проблемы

### KI-003 · Resolved · High · docker · образ PostgreSQL с pgvector

**Описание:** `postgres:17-alpine` не содержит расширения `vector`: миграция падала с
`extension "vector" is not available`.

**Решение:** образ заменён на `pgvector/pgvector:pg17`. В `downgrade` расширение не
удаляется (RULES §11.4).

**Создано:** 2026-10-29 · **Закрыто:** 2026-10-29

### KI-004 · Resolved · High · models, db · enum хранил имена вместо значений

**Описание:** SQLAlchemy `Enum(UserRole)` по умолчанию пишет **имя** члена (`STUDENT`),
тогда как в PostgreSQL тип создан со **значениями** (`student`). Вставка падала с
`invalid input value for enum userrole: "STUDENT"` (HTTP 500 на регистрации).

**Решение:** во всех enum-колонках указан
`values_callable=lambda enum_cls: [e.value for e in enum_cls]`.

**Создано:** 2026-10-29 · **Закрыто:** 2026-10-29

### KI-005 · Resolved · High · core/security, deps · passlib несовместим с bcrypt 5.x

**Описание:** `passlib 1.7.4` падает с `ValueError: password cannot be longer than 72 bytes`
и не читает версию bcrypt (`no attribute '__about__'`).

**Решение:** passlib удалён из зависимостей, хэширование выполняется напрямую через
`bcrypt` (`app/core/security.py`); длина пароля ограничена 72 байтами в Pydantic-схеме.

**Создано:** 2026-10-29 · **Закрыто:** 2026-10-29

### KI-011 · Resolved · Critical · api/auth · эскалация роли при регистрации

**Описание:** `POST /auth/register` принимал поле `role` из запроса, поэтому
любой мог зарегистрироваться с ролью `admin` или `teacher` и получить доступ к
админским эндпоинтам.

**Решение:** регистрация всегда создаёт `role=student`, `level=basic`; роль
меняется только администратором через `PATCH /users/{id}/role`.
Добавлен регрессионный тест `test_register_ignores_requested_role`.

**Создано:** 2026-10-29 · **Закрыто:** 2026-10-29
