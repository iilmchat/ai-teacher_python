## 1. Принципы

- **Факты — от кода, объяснения — от LLM.** Любой код, предложенный учеником,
  должен быть выполнен в sandbox и проверен. LLM не имеет права "придумывать"
  результат выполнения.
- **Уровень — это политика, а не только промпт.** Ответ ассистента определяется
  комбинацией промпта, анализа кода и образовательной стратегии уровня.
- **Источник истины — один.** Архитектурные решения — только в `Design.md`.
  Дублирование факта в нескольких документах запрещено; вместо этого — ссылка.
- **Не перескакивать через зависимости.** В `TODO.md` у каждой задачи указано
  `Зависит от:`. Если зависимость не закрыта — задача не начинается.
- **Блокер — это нормально.** Лучше завести `KI-NNN` и остановиться, чем
  обойти проблему "временным решением", которое потом забывается.
- **Маленькие итерации.** Одна итерация — один спринт из `TODO.md`.
  В конце итерации — зелёный CI и отчёт в `RELEASES.md`.
- **Код — на Python 3.12, Frontend — на React 19.** Не меняем стек без согласования.

## 2. Ветвление и коммиты

### 2.1. Ветки

- `main` — всегда зелёная, всегда готова к деплою.
- `sprint/N-<slug>` — рабочая ветка спринта. Пример:
  `sprint/01-project-setup`, `sprint/06-code-execution`.
- `fix/KI-NNN-<slug>` — исправление известной проблемы. Пример:
  `fix/KI-012-executor-timeout-overflow`.
- `exp/<slug>` — эксперименты, не идущие в `main` напрямую.

Мерж в `main` — только через PR с зелёным CI и ревью.

### 2.2. Сообщения коммитов — Conventional Commits

```
<type>(<scope>): <subject>

[optional body]

[optional footer: Refs: S-N-NNN, KI-NNN]
```

**Типы:** `feat`, `fix`, `chore`, `docs`, `test`, `refactor`, `perf`, `build`, `ci`.

**Scope** — модуль или задача: `auth`, `chat`, `code`, `tasks`, `frontend`, `docs`, `ci`.
Допускается `S1-001` вместо scope, если задача крупная.

**Примеры:**

```
feat(chat): implement WebSocket streaming for LLM responses (S4-006)
fix(executor): handle memory limit exceeded error (KI-007)
docs(rules): add commit message conventions
test(auth): cover JWT token refresh scenarios (S3-005)
```

**Запрещено:**
- Коммитить с `--no-verify` (pre-commit хуки обязательны).
- Коммитить секреты (`.env`, ключи, токены).
- Смешивать в одном коммите несвязанные изменения.

### 2.3. PR

- Название PR = `<type>(<scope>): <краткое описание> (S-N-NNN..S-M-MMM)`.
- В описании — ссылки на задачи из `TODO.md` и отчёт спринта.
- CI должен быть зелёным: обязательный набор — workflow **`CI (self-hosted
  fallback)`** (6 обязательных job'ов: Lint, Test, Frontend, Security, E2E,
  Docker; плюс advisory `Perf smoke (submit)`, S23-003).
  Красный CI — PR не мержится.
- Ревьюер проверяет чек-лист §10.

### 2.4. Стандарт отчётов по спринту (7 разделов)

> Каждый отчёт о спринте — строго 7 разделов:
> **(1) Файлы (+/-)** — созданные/изменённые пути;
> **(2) Покрытие** — новые/обновлённые тесты;
> **(3) Результаты** — Build 0/0 и Tests X/Y;
> **(4) Smoke** — ручной сценарий проверки;
> **(5) Что не так** — известные ограничения/риски;
> **(6) Новые KI** — зарегистрированные KI или "нет";
> **(7) Обоснование** — почему выбрана такая архитектура.
> Файл отчёта: `docs/reports/sprint-N/SPRINT-N.md`.

## 3. Код

### 3.1. Backend (Python 3.12)

- **Стиль:** `ruff` с конфигом из `pyproject.toml` (`line-length = 100`,
  `target-version = "py312"`). Нарушения — блокер для мержа.
- **Типы:** `mypy --strict` обязателен. Публичные функции и методы — с
  аннотациями. `Any` — только с `# type: ignore[...]` и комментарием.
- **Async:** весь I/O — `async`/`await`. Синхронные блокирующие вызовы
  — только через `asyncio.to_thread` / `run_in_executor`.
- **Pydantic v2:** все входы/выходы API — через `BaseModel`. Никаких
  "голых" `dict` в публичных сигнатурах.
- **SQLAlchemy 2.0:** `Mapped[...]`, `mapped_column`. Никаких старых
  `declarative_base()` и `Column(...)`.
- **Alembic:** одна миграция — одно логическое изменение. Автогенерация —
  только с ревью; ручные правки миграций допустимы.
- **Логи:** `structlog`, structured JSON. Никаких `print()`. Уровни:
  `debug` — для отладки, `info` — для бизнес-событий, `warning` — для
  восстановимых проблем, `error` — для сбоев.
- **Ошибки:** собственные исключения в `app/errors.py`. `HTTPException`
  только на уровне API.
- **Конфиг:** только через `Settings` (pydantic-settings). Чтение
  `os.environ` напрямую — запрещено.

### 3.2. Frontend (React 19 + TypeScript)

- **Стиль:** `tsc --noEmit` обязателен, `strict: true`. `any` — только с
  `// eslint-disable-next-line` и комментарием.
- **Компоненты:** функциональные, без классов. Хуки — по правилам React.
- **Состояние:** Zustand для глобального, `useState` для локального.
- **Запросы:** `fetch` обёрнут в `lib/api.ts` с типами. Ответы
  валидируются схемами.
- **Стили:** Tailwind CSS 4. Никаких inline-стилей, кроме экспериментов
  (которые не мержатся).
- **i18n:** все строки — через `react-i18next`. Хардкод строк в JSX —
  запрещён.
- **Производительность:** route-level code-split для страниц. Основной
  чанк — ≤ 200 kB (gzip).

### 3.3. Общее

- **Не менять стек** без явного согласования (Python 3.12, FastAPI, React 19,
  PostgreSQL 17 + pgvector, Redis, DeepSeek/LM Studio).
- **Не добавлять зависимости** без обоснования в PR.
- **Не коммитить сгенерированные файлы** (`dist/`, `__pycache__/`,
  `node_modules/`).
- **Не коммитить локальные данные** (`data/`, `.env`, `.venv/`).

## 4. Тесты

### 4.1. Обязательный минимум

- **Каждая новая функция/метод** — с unit-тестом. Если тривиальна — явно
  указать в PR.
- **Каждый эндпоинт API** — с интеграционным тестом (FastAPI TestClient).
- **Каждая миграция** — тест на `upgrade` + `downgrade` + повторный `upgrade`.
- **Каждый уровень ассистента** — тест на корректность промпта.
- **Каждый executor** — тест на безопасность (dangerous code blocked).

### 4.2. Пирамида

- **Unit** — 70%: чистая логика, без БД и сети.
- **Integration** — 25%: API + БД (testcontainers), LLM (mock).
- **E2E** — 5%: Playwright на фронтенде + полный сценарий.

### 4.3. Структура

```
tests/
├── unit/
│   ├── test_security.py
│   ├── test_executor.py
│   ├── test_levels.py
│   └── ...
├── integration/
│   ├── test_auth_api.py
│   ├── test_chat_api.py
│   ├── test_tasks_api.py
│   └── ...
├── e2e/
│   └── test_full_flow.py
└── fixtures/
    ├── sample_tasks.json
    └── ...
```

### 4.4. Правила

- **Тесты не должны зависеть от порядка выполнения.**
- **Тесты не должны ходить в интернет.** LLM — через моки.
- **Тесты не должны разделять состояние.**
- **Flaky-тесты — блокер.** Завести `KI-NNN`, починить или `@pytest.mark.skip`.
- **Покрытие:** целевое ≥ 80% для `app/`, ≥ 60% для `frontend/src/`.

## 6. Итерации и отчёты

### 6.1. Планирование

- Итерация = один спринт из плана этапа: `TODO.md` (v0.1.0) или
  `TODO_V0.2.md` (v0.2.0 и далее).
- **Один этап — один файл плана.** `TODO.md` содержит завершённые спринты
  1–10; новый этап начинается отдельным файлом `TODO_VX.Y.md`, чтобы история
  не смешивалась с текущими задачами.
- В начале спринта — план в `docs/RELEASES.md`: задачи, порядок, риски.
- Если задача оказалась больше — разбей на подзадачи (`S-N-NNNa`, `S-N-NNNb`)
  и обнови зависимости в файле плана текущего этапа.

### 6.2. Выполнение

- Работай по шагам, после каждого — проверяй результат (`ruff`, `mypy`,
  `pytest`, `pnpm typecheck`).
- Каждый шаг — отдельный коммит.
- Блокер — сразу `KI-NNN` и стоп.

### 6.3. Завершение спринта

Спринт завершён, когда:

1. Все задачи закрыты (`[x]` в плане этапа), или явно перенесены в
   `KNOWN_ISSUES.md` с `KI-NNN`.
2. `ruff check app tests`, `mypy app`, `pytest -q` — зелёные.
3. `pnpm --dir frontend typecheck && pnpm --dir frontend lint && pnpm --dir frontend test && pnpm --dir frontend build` — зелёные.
4. CI — зелёный.
5. Отчёт в `docs/RELEASES.md` заполнен + `docs/reports/sprint-N/SPRINT-N.md`.
6. `docs/CHANGELOG.md` обновлён.
7. PR в `main` создан и смержен.

### 6.4. Планирование следующего этапа

Перед стартом нового этапа (vX.Y):

1. Собрать открытые `KI-NNN` и разложить их по спринтам (сначала долг, потом фичи).
2. Создать `TODO_VX.Y.md` со структурой: цели этапа, карта KI → спринты,
   спринты с задачами/зависимостями/оценками, сквозной DoD, риски.
3. Обновить `docs/RELEASES.md` (таблица будущих спринтов) и `docs/README.md`
   (ссылка на новый план).
4. Согласовать порядок спринтов: закрытие долга идёт первым.

## 7. Безопасность

### 7.1. Секреты

- **Никогда** не коммитить `.env`, ключи API, пароли, токены.
- Все секреты — в ENV (dev) или Vault (prod).
- `.env.example` содержит только placeholder'ы (`change_me_*`).
- Pre-commit блокирует коммиты с паттернами реальных ключей.

### 7.2. Аутентификация и авторизация

- JWT + refresh-токены. Access — 30 минут, refresh — 7 дней.
- Роли: `student`, `teacher`, `admin`. Проверки — на уровне эндпоинта.
- Rate limiting: 5/мин на login, 300/мин общий.
- **Доступ учителя к ученику — через класс.** Проверки роли недостаточно:
  работы, комментарии и объявления доступны только владельцу класса, в
  котором состоит ученик (`get_student_for_teacher`), иначе 403;
  несуществующий/не-ученик — 404. `admin` классами не ограничен.
- **Массовые операции — отчёт, а не 4xx.** Частичный успех (уже в классе,
  неизвестный логин, повторное снятие) возвращается в `skipped`/`unknown`;
  лимит — 100 элементов на запрос (проверяется Pydantic).
- **Персональные данные — не в аудит.** В журнал пишутся действие, id и
  сводка (длины, количества), но не текст комментария и не списки логинов.

### 7.3. Code Execution Security

- **RestrictedPython** обязателен.
- Timeout: 5 секунд максимум.
- Memory limit: 128 MB.
- No file system, no network, no dangerous imports.
- Логировать попытки нарушения безопасности.

### 7.4. Валидация входных данных

- Все входы — через Pydantic-схемы с `strict=True`.
- Python код — валидируется перед выполнением.
- Загружаемые файлы — лимит размера (10 MB).

## 8. Работа с LLM

### 8.1. Общие правила

- **Промпты версионируются.** `app/services/llm/prompts/<level>.txt` — файлы.
- Изменение промпта — отдельный PR с тестом.
- **Стоимость контролируется.** `max_tokens` и `cost_cap` на запрос.
- **Fallback.** Если DeepSeek недоступен — fallback на LM Studio.

### 8.2. Три уровня

- **Basic:** наводящие вопросы, метафоры, аналогии. НЕ давать готовый код.
- **Intermediate:** объяснение с примерами, частичные решения.
- **Advanced:** полные решения с детальными объяснениями.

### 8.3. Контекст

- Сбор контекста из истории чата (последние N сообщений).
- Injection системного промпта в зависимости от уровня.
- Truncation для длинных диалогов.

## 9. Обработка блокеров

### 9.1. Что считается блокером

- Шаг не выполняется из-за внешней причины.
- Тест падает нестабильно (flaky).
- Обнаружено противоречие в `Design.md` или `TODO.md`.
- Обнаружена уязвимость или утечка секрета.

### 9.2. Что делать

1. **Завести `KI-NNN`** в `docs/KNOWN_ISSUES.md`.
2. **Пометить задачу** в `TODO.md` как `[~]` со ссылкой на `KI-NNN`.
3. **Остановиться.** Не обходить "временным решением".
4. **Сообщить.**

### 9.3. Severity

- **Critical** — блокирует весь проект.
- **High** — блокирует текущий спринт.
- **Med** — блокирует одну задачу.
- **Low** — не блокирует, но стоит починить.

## 11. Окружение и воспроизводимость

### 11.1. Адреса: `127.0.0.1`, а не `localhost`

На Windows `localhost` резолвится сначала в `::1`, а Docker Compose
публикует порты только на IPv4-loopback (`127.0.0.1`).

- `POSTGRES_HOST=127.0.0.1`, `REDIS_URL=redis://127.0.0.1:<port>/0`.
- В `docker-compose.yml` порты публикуются как
  `"127.0.0.1:${PORT:-default}:<container>"`.

### 11.2. Порты

- Канон: Postgres `5432`, Redis `6379`, API `8000`, Frontend `3000`.
- `.env` — локальный, в git не попадает; `.env.example` хранит канон.
- **Факт на текущей машине (KI-001):** `5432` занят контейнером `ticket-postgres`,
  `6379` — `workflow-builder-redis`. Поэтому проект использует
  Postgres `5434` и Redis `6381`.
- Чужой контейнер **не останавливаем**. Внешние порты берём из ENV:
  `POSTGRES_PORT`, `REDIS_PORT` — они подставляются в `docker-compose.yml`
  и читаются `Settings` (дефолты в `app/config.py` тоже `5434`/`6381`).
- Внутри compose-сети сервисы общаются по внутренним портам (`postgres:5432`,
  `redis:6379`) — их менять не нужно.
- Урок KI-001: если контейнер не смог опубликовать порт, подключение уходит
  на **чужой** сервис и падает с непонятной ошибкой аутентификации. Всегда
  проверяйте `docker compose ps` — в колонке PORTS должен быть `0.0.0.0:PORT->`
  или `127.0.0.1:PORT->`, а не голый `<port>/tcp`.

### 11.3. Python

- Python 3.12 обязателен; на текущей машине установлен 3.11.8 — тесты и сервис
  работают, но CI гоняет 3.12.
- Poetry или pip + venv.
- Версии библиотек фиксируются в `requirements.txt`.
- **PyPI с хоста может быть заблокирован** (KI-017): ставить/аудитить пакеты —
  через Docker (`python:3.12-slim`), wheelhouse-трюк и локальный
  `audit_python_deps.py`; см. §11.19.

### 11.4. Конфигурация: `.env` в корне проекта

- `app/config.py` читает `.env` по абсолютному пути
  (`Path(__file__).resolve().parents[2]`), а не относительно CWD. Иначе при
  запуске `alembic`/`pytest` из `backend/` настройки тихо подменяются
  дефолтами — так порт 5434 превращался в 5432 и запросы уходили в чужую БД.
- `allowed_origins` в `.env` задаётся CSV (`a,b`) — парсер в
  `Settings.parse_allowed_origins` поддерживает и JSON-массив.
- Конфиг `mypy` живёт в корневом `pyproject.toml`; mypy из `backend/`
  запускается с `--config-file ../pyproject.toml`, иначе строгие правила
  не применяются и ошибки типизации не ловятся.

### 11.5. База данных и миграции

Ловушки, на которые уже наступали:

1. **Образ Postgres.** `postgres:17-alpine` не содержит `pgvector` →
   `extension "vector" is not available`. Нужен `pgvector/pgvector:pg17` (KI-003).
2. **`server_default` для JSONB.** `server_default=sa.text("{}")` невалиден:
   нужен `sa.text("'{}'::jsonb")` (и `'[]'::jsonb` для массивов).
3. **Enum хранит имена, а не значения.** `Enum(Role)` пишет `STUDENT`, тогда как
   тип создан со значениями `student`. Обязательно
   `values_callable=lambda enum_cls: [e.value for e in enum_cls]` (KI-004).
4. **`metadata` — занятое имя** в `DeclarativeBase`. Колонку `metadata`
   объявляем как `session_metadata` с `mapped_column("metadata", ...)`.
5. **`create_all` не заменяет миграции.** Тесты создают схему из моделей и потому
   не видят расхождений с Alembic. Перед коммитом — `alembic check` (KI-002).
6. После любой правки миграции: `alembic upgrade head`, `alembic check`,
   `alembic downgrade base && alembic upgrade head`.
7. **Lazy-relationship в async — `MissingGreenlet`.** Обращение вида
   `if task.progress:` внутри async-сервиса падает. Используйте
   `selectinload` или отдельный запрос (`exists_for_task`), как в
   `TaskService.delete_task`.
8. **Данные для разработки — отдельный скрипт.** Учебные задачи добавляет
   `backend/scripts/seed_tasks.py` (идемпотентно, по заголовку), а не миграция
   (KI-010).
9. **Индексы — отдельной additive-миграцией.** 0009/0010 создают только
   индексы (и `ADD COLUMN IF NOT EXISTS` как страховку); downgrade удаляет
   индекс, но не колонку/расширение `vector`. Модели обязаны описывать те же
   индексы (`Index(...)` в `__table_args__`), иначе `alembic check` покажет
   расхождение. После ручных индексов всегда: `upgrade head`, `check`,
   `downgrade base && upgrade head`.

### 11.6. Пароли и bcrypt

- `passlib 1.7.4` несовместим с `bcrypt 5.x` (`ValueError` на 72+ байтах,
  `no attribute '__about__'`). Используем `bcrypt` напрямую (KI-005).
- bcrypt не принимает пароль длиннее 72 байт: ограничение продублировано
  в `UserCreate.password` (`max_length=72`), чтобы клиент получал 422, а не 500.

### 11.7. Тесты на Windows

- Тесты работают на реальном PostgreSQL (SQLite не поддерживает JSONB/VECTOR).
- Создание тестовой БД — синхронная session-scoped фикстура (`psycopg2`):
  async-фикстуры другого scope привязываются к чужому event loop и ломают asyncpg.
- Клиент в тестах — `httpx.AsyncClient` + `ASGITransport`; `TestClient` нельзя
  совмещать с async-фикстурой БД.
- Каждый тест выполняется в транзакции с откатом
  (`join_transaction_mode="create_savepoint"`), поэтому коммиты внутри
  репозиториев не «протекают» между тестами.

### 11.8. Песочница кода (RestrictedPython)

Ловушки, проверенные на практике:

1. **Поток нельзя убить.** `asyncio.wait_for` + `to_thread` не останавливает
   `while True`: поток продолжает работать, процесс живёт. Выполняем код в
   отдельном интерпретаторе и убиваем его по таймауту.
2. **`multiprocessing` + uvicorn на Windows.** `spawn` перезапускает
   `__main__` → «Safe importing of main module». Используем `subprocess` с
   `sys.executable -c`.
3. **`_print_` — это класс `PrintCollector`.** RP 7 сам инстанцирует его
   (`_print = _print_(_getattr_)`). Собранный вывод лежит в
   `globals['_print']` и доступен вызовом `globals['_print']()`.
4. **`+=` требует `_inplacevar_`.** Без guard'а падает
   `NameError: name '_inplacevar_' is not defined`.
5. **`safe_builtins` не содержит `print`** и большинства встроенных функций —
   дополняем явно, но никогда не добавляем `open`, `eval`, `exec`.
6. **Лимит памяти нельзя ставить процессу pytest.** `_run_restricted` по
   умолчанию лимит не применяет; это делает дочерний раннер
   (`apply_limits=True`). Иначе один тест ограничит весь прогон (S13-001).
7. **`RLIMIT_AS` ставится после импортов.** Ограничение на virtual memory
   ниже текущего потребления не даёт загрузить RestrictedPython; ставим в
   начале `_run_restricted`, но уже в дочернем процессе.
8. **Job Object нельзя навесить «потом».** На Windows процесс назначает себя
   в job сам (`AssignProcessToJobObject` + `GetCurrentProcess`), поэтому нет
   гонки с первым выделением памяти. Handle job держим глобально — иначе job
   уничтожается. Если процесс уже в несовместимом job, `memory_limit_enforced`
   = false, остаётся таймаут.
9. **`asyncio.Semaphore` между loop'ами ломается.** Ограничитель
   одновременных запусков — `threading.BoundedSemaphore` (pytest создаёт новый
   event loop на тест). Ожидание слота — через `asyncio.to_thread`.
10. **Вывод обрезается в дочернем процессе.** Нельзя отдавать 1 МБ stdout
    через JSON: `truncate_output` вызывается до сериализации, в ответе —
    флаг `output_truncated`.
11. **RestrictedPython 8.5 запрещает `.format()`.** `str.format`,
    `str.format_map` и `string.Formatter` блокируются целиком (закрыты обходы
    GHSA-hp3v-5vw7-fx9w, GHSA-ffg3-p8fm-mjx2). Это не баг: ученику нужна
    подсказка, поэтому `NotImplementedError` про формат переводится в
    `error_type=RestrictedFeatureError` + «используйте f-строки или `%`».
    F-строки/% работают, но dunder-доступ в них по-прежнему запрещён
    (`SecurityError`). Не «чинить» тестами, ожидающими старое поведение
    (KI-018, §11.19).
12. **Батч выполняет все кейсы одним процессом (S23-001).** Протокол —
    построчный JSON: на кейс одна строка результата, в конце `{"done": true}`.
    Таймаут **на кейс** держит родитель (иначе зависший кейс ждёт весь батч);
    при таймауте процесс убивается, текущий кейс — `TimeoutError`, остальные —
    `SandboxError` («не выполнялись»). Лимит памяти ставится один раз (на
    первом кейсе): RLIMIT_AS/Job Object нельзя ослабить или навесить дважды.
    Отдельный процесс нужен из-за `MemoryError`/`SystemExit`: `except
    BaseException` в воркере превращает их в результат кейса, а не в тихую
    смерть всего прогона.
13. **Пул тёплых интерпретаторов (S23-002) — только через `execute_many`.**
    Процесс живёт между задачами; изоляция — свежие `globals`/`builtins` на
    каждый вызов (утечки переменных между задачами нет). Процесс убивается
    после `TimeoutError`/`MemoryError`/сбоя протокола, после
    `EXECUTOR_POOL_MAX_TASKS` и при shutdown (`lifespan`). Пул привязан к event
    loop'у: pytest создаёт новый loop на тест — пулы закрытых loop'ов
    убиваются в `get_pool`, иначе копятся процессы.
14. **Фейковые исполнители в тестах обязаны реализовать `execute_many`.**
    `submit`/генерация идут батчевым путём; фейк, переопределивший только
    `execute`, молча вызовет настоящую песочницу (так «сломались» два теста
    прогресса при S23-001). В фейке `execute_many` = цикл по `execute`.
15. **Скорость песочницы измеряется, а не обещается.** Бюджет submit — 5 RPS,
    p95 ≤ 2000 мс (`scripts/load_test.py --scenario submit --rps 5`). После
    оптимизаций: батч — 395 мс, батч+пул — 49 мс (см.
    `docs/reports/sprint-23/LOAD_TEST-SUBMIT.md`).
16. **Контейнерный раннер — отдельное ядро (S24).** Образ
    `ai-teacher-sandbox-runner` собирается из `backend/sandbox_runner` и
    содержит только stdlib + RestrictedPython + `app/core/sandbox_runtime.py`.
    Не импортировать в это ядро `app.config`/`app.errors`/БД: контейнер не должен
    уметь ничего из стека приложения.
17. **Изоляция проверяется self-check'ом, а не доверием флагам.** `--self-check`
    внутри контейнера подтверждает `uid=65534`, read-only rootfs, доступный
    tmpfs, недоступную сеть и `CapEff=0`; CI (job `Docker build`) и
    `scripts/ci/docker.ps1` падают, если проверка не прошла.
18. **Windows: `shutil.which("docker")` возвращает шим без `.exe`.** CreateProcess
    на нём падает с `WinError 193`; ищите `docker.exe`/`docker.cmd`
    (`container_sandbox.docker_path`), иначе контейнерный режим ложно
    «недоступен» и всё уходит в fallback.

### 11.10. Frontend (pnpm 12, Vite 6, TS)

Ловушки, проверенные на практике:

1. **pnpm 12 блокирует build-скрипты.** `pnpm install` падает с
   `ERR_PNPM_IGNORED_BUILDS`. Настройки живут в `frontend/pnpm-workspace.yaml`
   (`onlyBuiltDependencies: [esbuild]`); разово — `pnpm install --allow-build=esbuild`.
2. **`defineConfig` для тестов.** Секция `test` типизируется только из
   `vitest/config`, иначе `tsc -b` падает на «'test' does not exist».
3. **Project references.** `pnpm build` = `tsc -b && vite build`;
   `vite.config.ts` проверяется отдельным `tsconfig.node.json` (нужен `@types/node`).
4. **Регистр директорий.** Windows не различает `Layout` и `layout`, Linux — да.
   Все каталоги `src/components/*` пишем в нижнем регистре (`components/layout`).
5. **Прокси в dev.** Vite проксирует `/api` → `http://127.0.0.1:8000`
   (`127.0.0.1`, не `localhost` — см. §11.1); CORS в dev не нужен.
6. **`import.meta.env`** требует `src/vite-env.d.ts` с объявлением `ImportMetaEnv`.
7. **Алиасы путей** задаются дважды: `tsconfig.app.json#paths` и `vite.config.ts#resolve.alias`.
8. **jsdom не реализует `scrollIntoView`** — в компонентах вызывайте его опционально
   (`el?.scrollIntoView?.(...)`), иначе тесты падают на монтировании.
9. **Правило react-refresh.** Файл с компонентом не должен экспортировать ещё и
   утилиты: `splitCodeFences` вынесена в `lib/markdown.ts`, иначе ESLint даёт warning.
10. **Monaco в тестах.** Lazy-компонент `MonacoEditor` мокается в
    `src/test/setup.ts` на `textarea`; сам Monaco в jsdom не грузим.
11. **Monaco офлайн.** `@monaco-editor/react` удалён; AMD-ассеты
    `monaco-editor/min/vs` копируются в `public/monaco/vs` (prebuild/predev),
    editor — lazy-чанк, worker — через `MonacoEnvironment.getWorkerUrl`.
    `pnpm test:offline` проверяет отсутствие CDN в `dist/assets`.
12. **Регистр имён файлов.** `TaskForm.tsx` и `taskForm.ts` на Windows — один
    файл для tsc, но два для Linux; типы формы вынесены в
    `taskFormTypes.ts`, чтобы не ловить TS1261.
13. **Vitest 4.** Апгрейд 3.2.7 → 4.1.12 (S20-001) не потребовал правок
    `vite.config.ts`/`tsconfig.*`: секция `test` из `vitest/config`, coverage
    thresholds и exclude работают; `vitest-axe` совместим. `pnpm audit` —
    0; entry после апгрейда — 78.71 kB gzip.
11. **`loadMe()` при старте.** Токен в localStorage ещё не значит «пользователь
    загружен»: `App.tsx` вызывает `loadMe()` в `useEffect`, иначе после F5
    `ProtectedRoute` навсегда остаётся в `initializing` (Spinner). Баг найден e2e.

### 11.11. E2E (Playwright)

1. **Отдельное окружение.** Backend поднимается на порту 8001 с БД
   `ai_teacher_e2e` и провайдером `echo`; frontend — на 3100 с проксированием.
   Порты 8000/3000 не занимаются, e2e не мешают разработке.
2. **Порт Vite передаётся флагом** (`pnpm dev --host 127.0.0.1 --port N --strictPort`):
   env `VITE_DEV_PORT` не всегда доходит до дочернего процесса.
3. **Интерпретатор backend** — из venv (`E2E_PYTHON` в CI переопределяет на
   системный `python`).
4. **Изоляция данных.** Каждый тест регистрирует уникального пользователя
   (`uniqueId()`); БД переиспользуется между прогонами.
5. **Мок тяжёлых виджетов.** В e2e-режиме (`VITE_E2E=1`) Monaco заменяется на
   `textarea[data-testid="code-input"]` — тесты не зависят от CDN (KI-013).
6. **E2E не должны попадать в Vitest:** `test.exclude` содержит `e2e/**`.

### 11.12. Rate limiting и Redis в тестах

- Тесты лимитов используют in-memory фейк Redis: реальный клиент между
  event loop'ами даёт `RuntimeError: Event loop is closed`.
- В остальных тестах `RATE_LIMIT_ENABLED=false` (autouse-фикстура), иначе
  лимит на login ломает прогон.
- Middleware обязан быть fail-open: Redis недоступен → запрос проходит с
  предупреждением, а не 500.

### 11.13. LLM: health, fallback, метрики (S12)

1. **Health не должен врать.** `not_configured` — если ключ пуст или равен
   заглушке из `.env.example`; ping выполняется только у настроенного
   провайдера. Результат кэшируется на 60 с — тесты сбрасывают кэш
   (`reset_health_cache()`), иначе статус «протекает» между тестами.
2. **`models.list()` — дешёвый ping.** Не генерировать токены ради health;
   сетевой вызов оборачивать в `asyncio.wait_for`.
3. **`stream_options` типизируется.** Для mypy нужен
   `ChatCompletionStreamOptionsParam`, а не `dict[str, bool]`; `usage`
   приходит в последнем чанке с пустым `choices`.
4. **Fallback в стриме — только до первого токена.** Если ответ уже начал
   приходить, переключение исказит текст: ошибка пробрасывается.
5. **Метрики — глобальное состояние процесса.** В тестах создавать свой
   `LLMMetrics` или вызывать `reset()`; не проверять точные миллисекунды.
6. **`ChatMessage.metadata` — занятое имя.** Атрибут модели называется
   `message_metadata` (колонка `metadata`); ответ API собирается явно через
   `ChatMessageResponse.from_message`, а не `model_validate` (иначе Pydantic
   прочитает `Base.metadata`).
7. **Два pytest-процесса одновременно ломают тестовую БД.** `conftest`
   пересоздаёт общую `ai_teacher_test`; прогоны (включая `--cov`) запускать
   последовательно.
8. **`basic`-нарушения не блокируют ответ.** Детектор только помечает
   `warnings` и пишет лог; средний и продвинутый уровни не ограничиваются.

### 11.14. Контент задач: импорт, seed, генерация, версии (S14)

1. **Импорт валидирует записи поштучно.** Одна битая задача не отменяет
   остальные; отчёт `{created, skipped, errors}` — часть контракта.
   Дубликаты определяются по заголовку (идемпотентность).
2. **YAML — через `yaml.safe_load`.** Никаких `load`/`unsafe_load`; для mypy
   модуль `yaml` в override (`pyproject.toml`), стабы не обязательны.
3. **Seed — не миграция.** Данные лежат в `app/data/seed_tasks.py`, сервис
   идемпотентен. `SEED_ON_START` выполняется в `lifespan`; ошибка seed
   логируется как warning и **не валит старт**.
4. **Генерация без проверки не сохраняется.** Эталонное решение обязательно
   прогоняется в песочнице на всех кейсах; невалидные задачи — в `rejected`.
   `count ≤ 5`, один LLM-вызов на запрос, без автоматических повторов.
5. **JSON от LLM чистится.** Снимать ```-обёртку, брать первый `[`…последний
   `]`; при ошибке — отчёт, а не 500.
6. **Версия — снимок ДО мутации.** `update_task` сохраняет `task_versions`
   до `setattr`, иначе история содержит уже изменённое состояние.
7. **Откат тоже создаёт версию.** Текущее состояние сохраняется перед
   восстановлением, иначе последнюю правку нельзя вернуть.
8. **Теги — JSONB + GIN, нижний регистр.** Фильтр `Task.tags.contains([tag])`;
   нормализация в схеме, а не в репозитории.

### 11.15. Классы и назначения (S16)

1. **Владелец — тоже участник** с ролью `owner` в `classroom_members`.
   Проверка членства и роли — в сервисе, не в роутере.
2. **Код класса — секрет вступления.** 6 символов без похожих (`O/0`, `I/1`),
   уникальность проверяется перед вставкой; сравнение — в верхнем регистре.
3. **Уникальность назначения.** `UNIQUE(classroom_id, task_id)`, дубликат —
   409; иначе задача дважды попадёт в матрицу.
4. **Прогресс класса — только владельцу.** Участник видит свои задания, не
   чужие оценки; 403 на `/progress`.
5. **Матрица — один срез прогресса.** Не N×M запросов: прогресс всех учеников
   по назначенным задачам читается одним `IN`.
6. **`overdue` вычисляется на сервере** (`due_at < now` и не `completed`),
   клиент только отображает.

### 11.16. Достижения и уведомления (S17)

1. **Справочник достижений — в миграции.** Тестовая схема создаётся
   `create_all`, поэтому `conftest` вставляет `app/data/achievements.py`
   после создания таблиц.
2. **Ошибка выдачи достижений не ломает submit.** Оценка обёрнута в try/except
   с warning: результат задачи важнее «плюшки».
3. **Серия дней — UTC+3 по датам `completed_at`.** Дубли в один день
   схлопываются; серия засчитывается, если последний день — сегодня/вчера.
4. **Уведомление о дедлайне — ленивое.** Создаётся при `GET /me/notifications`
   (≤72 ч); отдельного планировщика нет, дубликат — по `payload.assignment_id`.
5. **Чужое уведомление — 404**, а не 403: не раскрываем существование id.

### 11.17. UX, тема и доступность (S18)

1. **Тёмная тема — класс `dark` на `<html>` + CSS-переменные.** Старые экраны
   получают тёмные значения через слой совместимости в `index.css`; новые
   компоненты используют `--surface/--border/--app-fg`.
2. **Тема применяется до рендера.** `store/theme.ts` вызывает `applyTheme`
   при импорте; `main.tsx` импортирует его сайд-эффектом.
3. **Monaco — глобальный `monaco.editor.setTheme`,** а не метод инстанса:
   `editor.setTheme` в типизации отсутствует.
4. **`/dev/ui` не попадает в прод.** Ленивый импорт завёрнут в
   `import.meta.env.DEV ? lazy(...) : null`; проверка — отсутствие чанка
   `DevUiPage` после `pnpm build`.
5. **axe в jsdom:** `color-contrast` отключён (jsdom не считает цвета),
   контраст — ручной чек-лист; остальные правила проверяются.
6. **Мобильный чат:** сессии — drawer под `lg`, кнопка с `aria-expanded` и
   `aria-controls`; закрытие по overlay.

### 11.18. Кэш, RAG и нагрузка (S19)

1. **Fail-open без cooldown = скрытый таймаут на каждом запросе.** Если Redis
   упал, `cache_get_json`/`cache_set_json` не должны ждать соединение каждый
   раз: после первого сбоя кэш «остывает» 10 с (`CACHE_COOLDOWN_SECONDS`),
   счётчик `errors` растёт, API отвечает 200 без кэша.
2. **Ключ кэша списка задач обязан включать `user_id`.** В ответе есть статус
   прохождения конкретного ученика — без пользователя кэш «протекает» между
   учениками (баг был бы утечкой прогресса). В ключ входят все фильтры:
   `difficulty`, `category`, `tag`, `q` (нормализованный), `skip`, `limit`.
3. **Инвалидация — namespace, а не точечные ключи.** Мутации задач зовут
   `invalidate_tasks_cache()` (SCAN+DEL по `cache:tasks:*`) при create/update/
   delete/деактивации, restore версии, импорте и seed. `chat:levels`
   статический — не инвалидируется.
4. **Метрики кэша — в памяти процесса** (как LLM-метрики): при нескольких
   воркерах `/admin/analytics` показывает счётчики только своего процесса.
   В тестах `CACHE_ENABLED=false` autouse-фикстурой; тесты кэша подставляют
   in-memory FakeRedis (реальный клиент между event loop'ами ломается).
5. **Эмбеддинги — best-effort, никогда не блокируют чат.** Ошибка провайдера,
   таймаут, несовпадение размерности (`RAG_EMBEDDING_DIM` ≠ длины вектора)
   логируются и дают `None`; сообщение всё равно сохраняется/отправляется.
   Поиск при этом уходит в ILIKE, а не в 500.
6. **ILIKE — не только «флаг выключен».** Fallback включается при
   выключенном `RAG_ENABLED`, недоступном/упавшем провайдере, пустой
   семантической выдаче и размерностном mismatch. Так `/chat/search` никогда
   не возвращает пустоту из-за инфраструктуры.
7. **pgvector: HNSW, а не ivfflat.** Ivfflat требует обучающих данных
   (`lists`) и на пустой/маленькой таблице бесполезен; HNSW строится сразу и
   поддерживает `vector_cosine_ops` (косинус — штатная метрика текстовых
   эмбеддингов). Колонка `embedding` nullable и существует с миграции 001;
   0010 делает `ADD COLUMN IF NOT EXISTS` и создаёт индекс.
8. **EXPLAIN на пустой БД врёт.** На 5–6 строках планировщик выбирает Seq
   Scan; доказывать индекс нужно планом с `SET LOCAL enable_seqscan=off` или
   реальным Bitmap/Index Scan там, где данных хватило. Не «чинить» индекс,
   пока не проверен план без seqscan.
9. **Нагрузочный раннер — httpx, а не k6/locust.** PyPI с хоста заблокирован
   (KI-017): k6/locust не поставить. `backend/scripts/load_test.py` на уже
   установленном httpx (asyncio), фиксированная длительность, p50/p95/p99,
   error rate, exit-код по бюджету. Запускать с `LLM_PROVIDER=echo`,
   `RATE_LIMIT_ENABLED=false`, отдельным backend/БД; submit CPU-bound —
   мерять отдельно от health, не делать выводов по одному прогону.
10. **Два pytest-процесса ломают тестовую БД** (общая `ai_teacher_test`
    пересоздаётся) — прогоны последовательно, включая тесты кэша/RAG.

### 11.19. Безопасность и релиз (S20)

1. **PyPI на хосте может быть заблокирован.** Аудит backend тогда выполняется
   в контейнере `python:3.12-slim` (тот же путь, что в CI), а для разработчика
   есть `scripts/audit_python_deps.py` по GitHub Advisory API. Не выдавать
   частичный результат за «чисто»: при исчерпании лимита скрипт возвращает
   exit 2; авторитетный результат — `pip-audit` в CI/контейнере.
2. **Wheelhouse-трюк.** Если пакет нужен локально, а PyPI недоступен:
   `pip download --no-deps` в контейнере → перенести wheel'ы →
   `pip install --no-index --find-links . wheel` → `pip check`, затем удалить
   `.wheelhouse`. Версии сверять с `requirements.txt`.
3. **`--ignore-vuln` в CI — временный и обоснованный.** Каждый игнорируемый ID
   документируется (KI + отчёт аудита), а после апгрейда удаляется из списка,
   иначе job «прячет» уже исправленные уязвимости. Итог формулировать точно:
   «0 critical, high только в транзитивном starlette с неприменимыми
   векторами, риск принят» — не «аудит полностью чистый».
4. **GitHub Advisory API — 60 запросов/час.** Скрипт кэширует advisories
   (`%TEMP%`), сохраняет курсор и умеет `--resume`/`--offline`; withdrawn-
   записи пропускаются; при неполных данных — exit 2, а не «0 находок».
   User-Agent обязателен; без токена лимит быстро исчерпывается.
5. **CSP и Monaco.** `unsafe-eval` не нужен: AMD-loader и worker'ы Monaco
   обслуживаются с собственного origin (`/monaco/vs`, worker через `blob:`).
   `style-src 'unsafe-inline'` нужен React/Tailwind/Monaco. Проверка —
   Playwright (`MONACO_LOADED: true`, 0 console errors) + отсутствие inline-
   скриптов в `dist/index.html`. CSP ломает Monaco тихо — проверять живьём.
6. **Наследование `add_header` в nginx.** Любой `add_header` в `location`
   отменяет наследование серверных заголовков безопасности. Поэтому кэш
   `/assets/` — через `expires 1y`, а не `add_header Cache-Control`; заголовки
   задаются на уровне `server` и дублируются флагом `always`.
7. **gitleaks: allowlist — только для плейсхолдеров.** `[extend] useDefault` +
   проектные правила; в allowlist — `change_me_*`, `your_*_here`, тестовые
   значения CI, пути `node_modules`/`venv`/`dist`. Обязателен негативный
   контроль: фейковые ключи должны ловиться. Скан истории — `fetch-depth: 0`;
   настоящий секрет не добавлять в allowlist, а отзывать/чистить историю.
8. **`restore.sh` — только в scratch-БД.** Guards: рабочую `ai_teacher` без
   `--force` не перезаписывать, запрет `postgres`/`template0`/`template1`,
   подтверждение без `-y`, коды 0/1/2, `--verify` со счётчиками таблиц/строк.
   Перед `pg_dump` проверять, что контейнер запущен (KI-001: иначе дамп может
   уйти в чужую БД).
9. **RestrictedPython 8.5 меняет поведение песочницы.** `.format()`/
   `format_map`/`string.Formatter` запрещены — это ожидаемо (KI-018); не
   возвращать их ради «удобства». Подсказка (`RestrictedFeatureError`) и
   тесты на f-строки/% — обязательны; dunder в f-строках остаётся запрещён.
10. **CI работает на self-hosted runner'е.** GitHub-hosted минуты заблокированы
    биллингом (KI-014), поэтому PR-гейты выполняет `ci-selfhosted.yml` на
    Windows-runner'е (`C:\actions-runner`, сессия пользователя — Docker Desktop
    и Playwright). `security`-эквивалент локально: `pip-audit` в контейнере,
    `gitleaks` по истории, `pnpm audit --audit-level=high`. Required checks на
    GitHub Free/private недоступны (403) — гейт обеспечивает GitFlic-пилот
    (KI-023); до этого мерж без зелёного CI — нарушение, а не «допущение».
    Эксплуатация, перезапуск и wheelhouse — §11.20 и `docs/CI.md`.

### 11.20. CI: платформа, гейты, runner (S21)

1. **Биллинг GitHub не лечится кодом.** Hosted-job'ы падают за 2–4 с с
   аннотацией про payments/spending limit; признак — `Test`/`Docker` = skipped.
   Проверять аннотацию API (`check-runs/<id>/annotations`), а не только текст
   в UI. Обход — self-hosted runner: его минуты не тарифицируются.
2. **Lint-job ставит runtime-зависимости.** Без `pip install -r
   backend/requirements.txt` mypy даёт ~295 `import-not-found`
   (fastapi/sqlalchemy/structlog). ruff/mypy при этом закреплены в
   `requirements.txt` — не ставить их «последними версиями»: unpinned ruff
   находил 54 «ошибки» на неизменённом коде.
3. **Runner — в сессии пользователя, не службой LocalSystem.** Иначе нет
   доступа к Docker Desktop (npipe), Playwright-браузерам и профилю pnpm.
   Процесс `Runner.Listener`, запуск `C:\actions-runner\run.cmd`.
4. **PyPI нестабилен (KI-017) — офлайн-first.** Job'ы сначала ставят
   зависимости из wheelhouse (named volume `ai-teacher-wheelhouse`,
   `/wheelhouse`), и только потом идут в PyPI. Колеса качает **Linux**-контейнер
   (`scripts/ci/build-wheelhouse.ps1`): Windows-wheelhouse даёт «not a supported
   wheel». pip-кэш — тоже named volume; сброс `docker volume rm`.
5. **Кэш между прогонами — named volumes, а не actions/cache.** На self-hosted
   проще и надёжнее: `ai-teacher-pip-cache`, `ai-teacher-pnpm-store`.
6. **Path-фильтры обязательны.** docs-only PR не гоняет e2e/docker
   (`paths-ignore: docs/**, **.md` в GitHub; `rules: changes:` в GitFlic).
7. **Required checks на GitHub Free/private нет.** `PUT .../protection` → 403.
   Скрипт `scripts/ci/protect-branch.ps1` содержит готовый payload; гейт мержа —
   GitFlic (KI-023). Не выдавать «зелёный CI» за «гейт включён».
8. **Релиз — из журнала, а не из коммитов.** Версия сверяется в трёх местах
   (`pyproject.toml`, `frontend/package.json`, `backend/app/config.py`);
   заметки — раздел «## Релиз vX.Y.Z» в `docs/RELEASES.md`; dry-run — по
   умолчанию, тег `v*-dryrun` — репетиция, повторный номер тега запрещён.
9. **Не дублировать гейты в release.** `release.yml` вызывает
   `ci-selfhosted.yml` через `workflow_call` — один набор команд для PR и релиза.
10. **Диагностика залипшего job:** `docker ps` (контейнер job'а), `docker logs
    <name>`, `C:\actions-runner\_diag\Runner_*.log`; отмена — `gh run cancel`,
    перезапуск — `gh run rerun <id> --failed`.

### 11.21. Обновление зависимостей (S22)

1. **Апгрейд — только с контрактными тестами.** `pytest -q tests/test_contract_openapi.py`
   (снапшот OpenAPI, 68 операций) и `tests/test_api_contract_shapes.py`
   (21 форма ответов) запускаются **до** и **после** апгрейда. Breaking-изменение
   без осознанного обновления снапшота — блокер мержа.
2. **Порядок апгрейда:** контрактные тесты → `pip install` новых пинов в venv
   (или wheelhouse) → `pytest -q` → e2e → обновление `requirements.txt` →
   `pip-audit` без игноров → CHANGELOG/SPEC/KNOWN_ISSUES. Один апгрейд — один PR.
3. **Снапшот обновляется осознанно, отдельным коммитом.** `python
   scripts/snapshot_openapi.py`; в коммите — почему изменение аддитивное
   (пример S22-002: `format: password`, `contentMediaType`,
   `ValidationError.ctx/input` — косметика OpenAPI, без удаления полей).
4. **Поведенческие изменения — в SPEC и тесты.** Апгрейд `starlette 1.x` дал
   **401 вместо 403** без заголовка `Authorization` (RFC 7235). Такое
   фиксируется в SPEC §7, тесте `test_access_matrix` и CHANGELOG, а не
   «замалчивается» зелёным pytest.
5. **`--ignore-vuln` — только с KI и датой.** С S22-002/003 в CI игноров нет;
   если появится новый advisory без исправления — завести KI, обосновать
   неприменимость вектора и указать, когда игнор снимается.
6. **Wheelhouse для офлайн-установки.** `python scripts/wheelhouse.py build
   --out .wheelhouse --docker` (Linux-колёса) + `install --no-index`;
   для CI — named volume `ai-teacher-wheelhouse` (`scripts/ci/build-wheelhouse.ps1`).
   Колёса, собранные pip'ом Windows-хоста, в Linux-контейнер не ставятся.
7. **Dependabot:** minor/patch — группой, мерж после зелёного CI; major —
   отдельным PR и ручной проверкой конфигов; авто-мерж на GitHub Free/private
   недоступен (KI-023), поэтому «зелёный + review» остаётся ручным правилом.
8. **`filterwarnings = error` пока не включаем.** В коде ~1 400 предупреждений
   `datetime.utcnow()`; сначала чистка, потом строгий режим — иначе шум
   предупреждений превратится в красный CI.

### 11.22. Наблюдаемость и аудит (S25)

1. **structlog.configure обязателен.** Без `merge_contextvars` привязанный
   `request_id` не попадает в записи; конфигурация — `app/core/logging.py`,
   вызывается при импорте `app.main`.
2. **Request-ID — в ответе, контексте и логах.** Клиент присылает `X-Request-ID`
   (для сквозной трассировки), сервер возвращает его же; middleware пишет
   `http_request` с длительностью — это основа для разбора инцидентов.
3. **Метрики не должны ломать scrape.** Сбор in-memory счётчиков обёрнут в
   try/except: сбой моста (LLM/кэш/пул) даёт warning, но `/metrics` отвечает 200.
4. **`/metrics` — внутренний эндпоинт.** Без авторизации, но в nginx
   `location = /metrics { return 404; }` и `/health/` закрыты; публиковать его
   наружу нельзя (раскрывает маршруты и нагрузку).
5. **Readiness проверяет зависимости, liveness — нет.** `/health/live` не должен
   ходить в БД/Redis (иначе падение зависимости перезапустит живой процесс);
   `/health/ready` отдаёт 503 со списком `checks`.
6. **Аудит пишется отдельным коммитом в той же сессии.** Репозитории коммитят
   действие сами; `record_audit` коммитит запись и при ошибке делает rollback с
   warning — аудит не должен валить действие.
7. **В payload аудита нет PII и секретов.** Только сводка: роль, ids, имена
   полей; никаких паролей, токенов, текстов решений.

### 11.23. Данные, экспорт и retention (S26)

1. **Экспорт — только admin, и каждое скачивание в аудите.** Стриминг через
   серверный курсор (`db.stream`), а не `fetchall`: выгрузка не должна
   исчерпывать память API. Лимит `EXPORT_MAX_ROWS` — обязателен.
2. **Отчёт класса — владельцу.** Ученик-участник получает 403, как и на
   `/progress`; отчёт аудируется (`classroom.report_exported`).
3. **CSV для людей — `utf-8-sig`.** Excel иначе ломает кириллицу; даты — ISO.
4. **Retention — отдельный скрипт, не код запроса.** Очистка не должна
   конкурировать с API за транзакции; удаление батчами (`--batch-size`),
   обязательный `--dry-run` перед первым запуском, `0` — выключено.
5. **Аудит — отдельно от retention-настроек остальных таблиц.** Журнал
   действий хранится дольше пользовательских данных (365 дней), иначе разбор
   инцидентов задним числом невозможен.
6. **Удаление аккаунта — анонимизация, а не каскад.** Username/email
   заменяются заглушками, пароль сбрасывается, `is_active=false` (401 на всех
   защищённых маршрутах). Прогресс сохраняет `user_id` — данные остаются
   обезличенными, а не исчезают вместе с историей класса.
7. **Новая таблица с ПДн — в PRIVACY.md.** Срок хранения и основание
   обработки фиксируются в `docs/PRIVACY.md`, иначе данные копятся бесконтрольно.

### 11.24. RAG: backfill и порог (S27)

1. **Backfill идемпотентен.** Только `embedding IS NULL`; обработанные id
   исключаются из следующих батчей — иначе dry-run и сбои провайдера дают
   бесконечный цикл (RULES §11.24 п.1 — проверено тестом).
2. **Ошибка эмбеддинга не рвёт прогон.** Считаем `errors`, продолжаем; повторный
   запуск доберёт пропущенное.
3. **Порог — до fallback.** `RAG_MIN_SCORE` фильтрует семантику, и только
   пустой результат уходит в ILIKE; иначе «слабые» попадания блокировали бы
   честный поиск по подстроке.
4. **Фикстуры качества обязательны.** Новые изменения поиска сопровождаются
   запросами/ожидаемыми сообщениями в `tests/fixtures/rag_queries.json` и
   проверкой precision@k — иначе регрессию не заметить.
5. **UI-поиск не шлёт запросов на каждый символ.** Только по submit; результат
   объявляется через `aria-live`, подсветка — `<mark>` (a11y, S27-003).

### 11.25. Массовые операции и уведомления (S28)

1. **Массовые действия идемпотентны.** Повторный вызов не создаёт дубликатов:
   уже назначенные и повторяющиеся в запросе id попадают в `skipped`, а не в
   ошибку. Клиент показывает отчёт `{created, skipped, unknown}`.
2. **Один коммит на пачку.** `add_assignments_bulk` добавляет все назначения и
   коммитит один раз; уведомления — после успешного коммита.
3. **Шаблоны не держат FK на задачи.** `task_ids` — JSONB; при применении
   отсутствующие задачи `unknown`, шаблон не ломается.
4. **Email — best-effort.** SMTP-ошибка логируется и не меняет ответ API
   (тест `test_email_failure_does_not_break_assignment`); флаг
   `NOTIFICATIONS_EMAIL_ENABLED` выключен по умолчанию.
5. **Журнал — только владельцу/админу.** CSV использует тот же формат, что
   отчёт класса (S26-002), и аудируется (`gradebook.exported`).

### 11.26. i18n, адаптивные таблицы и контраст (S29)

1. **Кириллица — только в локалях.** Любой текст в `src/**` идёт через
   `useTranslation`/`i18n.t`; аудит `scripts/check-i18n.mjs` в CI ловит
   нарушение (allowlist — только учебные примеры кода).
2. **Паритет ru/en обязателен.** Новый ключ добавляется в оба файла сразу;
   аудит падает при расхождении.
3. **Таблицы — через `Table`/`Tr`/`Td`/`Th`.** Только они дают карточки на
   мобильных (`data-cards`, `data-label`); «сырые» `<table>` не адаптируются.
4. **Контраст проверяется автоматически.** Новые страницы/темы добавляются в
   `e2e/a11y-contrast.spec.ts`; axe `color-contrast` должен давать 0 нарушений.
5. **e2e a11y терпимы к данным, но не к регрессиям.** Если данных нет (пустой
   список), тест `skip`; структурные проверки (skip-link, меню, карточки)
   обязательны.

### 11.27. Supply chain: digest и non-root (S33)

1. **Образ закрепляется по digest, тег — только для читаемости.**
   `python:3.12-slim@sha256:…`; тег без digest перезаписывается upstream и делает
   сборку невоспроизводимой. Digest обязателен для `FROM` в Dockerfile'ах и
   `image:` в compose-файлах.
2. **Обновление digest — осознанное действие, а не побочный эффект сборки.**
   `docker pull <tag>`, затем
   `docker image inspect <tag> --format '{{index .RepoDigests 0}}'`; обновить все
   вхождения, пересобрать затронутые образы, прогнать
   `python backend/scripts/check_image_pins.py`. Пиннинг **не заменяет** апгрейд:
   смена версии образа — отдельный шаг с тестами.
3. **Guard в CI, а не память.** `backend/scripts/check_image_pins.py` проверяет
   `FROM` и `image:` (5 файлов: backend/frontend/sandbox-runner Dockerfile'ы и
   оба compose). Новый Dockerfile/compose добавляется в списки скрипта; вызов —
   в `scripts/ci/backend-lint.sh` до установки зависимостей.
4. **Backend работает под non-root.** UID/GID `10001` (`USER app`), `/app` для
   процесса read-only, запись — только в `/tmp` (или `PROMETHEUS_MULTIPROC_DIR`).
   `PYTHONDONTWRITEBYTECODE=1` обязателен, иначе `__pycache__` в `/app` даёт
   предупреждения. Entrypoint и healthcheck выполняются тем же пользователем.
5. **Non-root проверяется командой, а не глазами:** `docker run --entrypoint id`
   (`uid=10001`), `touch /tmp/...`, `[ -w /app ]` → false, `alembic check`,
   `/health/ready` → 200. Полный `pytest` в собранном образе — с репозиторием,
   смонтированным read-only, и `-p no:cacheprovider` (иначе pytest пытается
   писать кэш в `/app`).

### 11.28. Пробная проверка задачи (S42-001)

`POST /tasks/{id}/check` — прогон тест-кейсов без траты попытки.

- Разница с `POST /tasks/{id}/submit` только в учёте прогресса: счётчик
  попыток и статус задачи не меняются, запись прогресса не создаётся,
  достижения не начисляются. Разбор по кейсам возвращается тот же.
- Общий код: `TaskService._run_cases` и `TaskService._build_message` —
  `submit_solution` и `check_solution` не дублируют логику.
- В ответе `SubmitResponse.practice = true` — по нему UI отличает пробу
  от отправки.
- Лимит — 20 пробных проверок в минуту на пользователя
  (`app/core/rate_limiter.py`: `CHECK_LIMIT`, `is_user_limited`),
  fail-open как и остальные лимиты; при превышении — 429 с
  `Retry-After: 60`.
- Кнопка отправки решения называется «Отправить решение», пробная —
  «Пробная проверка» (формулировки в `ru.json`/`en.json` и
  `docs/USER_GUIDE.md` должны совпадать).

### 11.29. Сборка фронтенда: чанки (S42-001)

- `manualChunks` в `frontend/vite.config.ts`: `react`, `i18n`, `stores`.
  Сторы вынесены отдельным чанком: иначе рост состояния (черновики,

- После изменения состава чанков проверить `pnpm build` и зафиксировать

### 11.30. История попыток (S42-002)

`GET /tasks/{id}/attempts` — постраничный список попыток текущего
ученика (новые сверху), `GET /tasks/{id}/attempts/{attempt_id}` —
детальная попытка с кодом и разбором по кейсам.

- Таблица `task_attempts` (миграция `014`) хранит **засчитанные**
  отправки: код, результат по каждому тест-кейсу, время. Сводка
  прогресса остаётся в `user_task_progress`.
- Пробная проверка (S42-001) попытку не засчитывает и в историю не
  пишется — это осознанное поведение, а не пропуск.
- Попытка принадлежит ученику: чужая недоступна (404) — по
  идентификатору нельзя проверить существование чужой записи.
- Таблица попадает под retention: `RETENTION_TASK_ATTEMPTS_DAYS`
  (default 90, `0` — не удалять); запись в `docs/PRIVACY.md`.
### 11.31. Автосохранение черновика (S42-003)

`PATCH /tasks/{id}/draft` — сохранить черновик решения,
`DELETE /tasks/{id}/draft` — удалить его.

- Колонки `draft_code` и `draft_updated_at` в `user_task_progress`
  (миграция `015`). Лимит — 20 000 символов, как и у кода решения.
- Черновик **не является решением**: счётчик попыток и статус задачи не
  меняются, запись в `task_attempts` не создаётся, в `best_solution` не
  попадает. При успешной отправке черновик очищается.
- Черновик лежит в строке прогресса, поэтому задача с черновиком
  удаляется мягко (`is_active=false`) — работа ученика сохраняется.
- Интерфейс: восстановление черновика приоритетнее `solution_template`,
  автосохранение с паузой 800 мс, сохранение при уходе со страницы
  (`beforeunload`), индикатор «Черновик сохранён в HH:MM» и кнопка
  «Удалить черновик».
### 11.32. Фильтры каталога задач (S42-004)

`GET /tasks` принимает фильтры `difficulty`, `category`, `tag`, `q`,
`status` (S42-004), `skip` и `limit`.

- Фильтр `status` отбирает задачи по прогрессу **того ученика**, который
  сделал запрос, и требует `user_id` в репозитории. Без записи прогресса
  задача считается `not_started`.
- Ключ кэша списка задач включает пользователя, все фильтры и статус:
  выдача у разных учеников по одному фильтру различается.
- Интерфейс: строка поиска с задержкой ввода 300 мс, фильтры категории,
  тега и статуса, счётчик найденного, кнопка «Сбросить фильтры» и
  отдельное пустое состояние с подсказкой. Фильтры отражаются в query-
  параметрах URL — ссылкой можно поделиться; при открытии страницы фильтры
  читаются из URL.
- Устаревшие запросы каталога отменяются через `AbortController`:
  ответ, пришедший позже свежего, не должен подменять результат.

### 11.33. Рекомендации следующих задач (S42-005)

`GET /tasks/recommended` — до 5 задач, которые стоит решить дальше.

- Правила детерминированные, без случайности: решённые задачи не
  рекомендуются; сложность не выше, чем у последней решённой + одна
  ступень; приоритет — начатые задачи, затем совпадение тегов с недавно
  решёнными, затем близость по сложности; при равенстве — по дате
  создания и id. Один и тот же прогресс всегда даёт один и тот же
  порядок.
- «Последняя решённая» — по времени решения ученика (`completed_at`),
  а не по дате создания задачи.
- Каждая рекомендация объясняет выбор: `reason` (`continue`,
  `same_topic`, `easier`, `next_step`, `starter`) и `reason_text`.
- Маршрут объявлен **до** `GET /tasks/{task_id}`: иначе путь
  `/tasks/recommended` попытался бы разобрать `recommended` как UUID.
- Интерфейс: блок «Рекомендуем дальше» на дашборде и на странице
  задачи; при отсутствии кандидатов — подсказка решить вводную задачу.

### 11.34. Связка задачи и ассистента (S42-006)

Deep-link `/chat?task=<task_id>` и кнопка «Спросить ассистента» на странице
задачи и в результатах проверки.

- Backend принимает **только `task_id`**, а не готовый текст контекста:
  задача загружается на сервере и должна быть активной, иначе 404. Клиент
  не может подсунуть произвольное «условие» или чужую задачу.
- Условие уходит в LLM отдельным `system`-сообщением сразу после промпта
  уровня. В `content` вопроса и в историю диалога оно не попадает.
- В контекст входят название, сложность, категория, описание и входные
  данные тест-кейсов. `solution_template`, `expected_output` и `hints`
  передавать **запрещено**: ассистент помогает разобраться, а не выдаёт
  готовый ответ. Лимиты — 4000 символов и 20 кейсов.
- В `message_metadata` сообщения ученика хранится только
  `{"task_context": {"task_id": "...", "title": "..."}}` — без кода ученика
  и без условия целиком. В лог пишется только `task_id`, без PII.
- Оба пути — REST `POST /chat/sessions/{id}/messages` и WebSocket
  `{"type":"chat","content":...,"task_id":...}` — передают `task_id` и
  сохраняют одинаковые метаданные.
- Фронтенд хранит контекст в сторе чата, показывает плашку с названием и
  снимает её кнопкой «Убрать»; снятие удаляет `task` из query-параметров
  через `replace`, чтобы «назад» не возвращало контекст. Deep-link не
  создаёт сессию автоматически — ученик нажимает «Новый чат».
- Идентификатор и название задачи не являются персональными данными,
  поэтому `docs/PRIVACY.md` не меняется.

### 11.35. Заголовки и управление сессиями чата (S43-001)

Сессия чата — управляемая сущность: у неё есть заголовок и признак
закрепления, а список сессий отсортирован предсказуемо.

- **Поля.** `chat_sessions.title` — nullable `String(120)`;
  `chat_sessions.pinned` — `boolean not null default false`. Миграция
  аддитивная (`016`), индекс `(user_id, pinned, updated_at)` обслуживает
  сортировку списка.
- **Авто-заголовок.** Берётся из **первого** сообщения ученика: текст
  схлопывается в одну строку (пробелы) и обрезается до 60 символов. Если
  заголовок уже задан вручную, сообщения его не перезаписывают.
- **Сортировка.** `GET /chat/sessions`: закреплённые сверху, остальные по
  `updated_at` (новые сверху). `updated_at` меняется при появлении нового
  сообщения; переименование и закрепление порядок не меняют — иначе чат
  «прыгал» бы вверх при каждом переименовании.
- **PATCH.** `PATCH /chat/sessions/{id}` с телом `{title?, pinned?}`; хотя бы
  одно поле обязательно (пустое тело — 422). `title: null` означает «не
  менять», а не «очистить»; пустая строка после trim — 422, длиннее 120
  символов — 422.
- **Изоляция.** Чужая сессия — 403 (как и на остальных маршрутах чата),
  несуществующая — 404.
- **UI.** Список сессий показывает заголовок, кнопки переименования,
  закрепления и удаления; удаление — только после подтверждения
  (`window.confirm`), закрепление отмечено значком «📌».

### 11.36. Остановка генерации и регенерация ответа (S43-002)

Ученик может прервать затянувшийся ответ и попросить ответить заново.

- **Остановка — по команде, а не разрывом соединения.** Клиент шлёт
  `{"type":"stop"}`; сервер прерывает поток на ближайшей дельте, сохраняет
  полученный текст и отвечает `{"type":"stopped","content":"…"}`. Соединение
  остаётся живым — после остановки можно писать дальше.
- **Генерация идёт в отдельной задаче.** Пока идёт стрим, сервер обязан
  принимать сообщения сокета: иначе команда `stop` не была бы прочитана.
  Одновременная генерация в одном соединении запрещена.
- **Частичный ответ сохраняется всегда.** Разрыв соединения во время
  генерации — тоже остановка: сервер фиксирует полученный текст с пометкой
  `metadata.stopped = true`. Пустой текст ответом не считается.
- **Пометка в метаданных, а не отдельная таблица.** Признак остановки и
  признак замены ответа живут в `message_metadata` сообщения: этого хватает
  для интерфейса и не требует новой миграции.
- **Регенерация не дублирует вопрос.** Новый ответ строится на том же
  контексте, что и первый, и на том же уровне; вопрос ученика в историю не
  добавляется повторно. Прежний ответ в контекст LLM не попадает.
- **Прежний ответ не удаляется.** Он остаётся в истории с `replaced = true`
  и `replaced_by` — так видно, что ответ меняли, и его можно изучить.
- **Изоляция.** Регенерация в чужой сессии — 403, неизвестное сообщение —
  404, попытка перегенерировать вопрос ученика — 422.
- **Порядок сообщений в диалоге** задаётся `order_by` в relationship
  `ChatSession.messages`: без него PostgreSQL отдаёт строки в физическом
  порядке, а он не гарантирован.

### 11.37. Оценка ответов ассистента (S43-003)

Ученик оценивает ответ ассистента, администратор видит сводку качества.

- **Оценка принадлежит ученику.** Таблица `message_feedback` хранит пары
  «сообщение × ученик» с уникальным ограничением: на одно сообщение у
  одного ученика оценка всегда одна. Повторная оценка **меняет** значение,
  а не добавляет строку.
- **Оценивать можно только ответ ассистента в своей сессии.** Чужое
  сообщение — 403, неизвестное — 404, вопрос ученика — 422.
- **Значение ограничено CHECK-constraint** `value IN (-1, 1)`; комментарий —
  до 500 символов. Ни то, ни другое не является персональными данными
  (текст ответа ассистента и мнение ученика о нём), поэтому
  `docs/PRIVACY.md` не меняется.
- **Оценка не влияет на ответ.** Оценка не меняет текст ответа и не
  скрывает его: это сигнал качества, а не модерация.
- **Сводка качества — только для администратора.** `GET /admin/quality`
  отдаёт счётчики, доли одобрения и срезы по провайдеру и модели (они берутся
  из `metadata` ответа). Негативные оценки с текстом ответа — вход для
  LLM-as-judge (см. `docs/LLM_EVAL.md`), а не способ показать ученику чужую
  оценку.
- **Клиенту нужен настоящий id сообщения.** Ответ, пришедший по WebSocket,
  сервер сохраняет сам, поэтому в событии `done`/`stopped` передаётся
  `message_id` сохранённого сообщения: локальный идентификатор не годится
  для оценки.

### 11.38. Выгрузка диалога и шаблоны промптов (S43-004)

Диалог можно забрать с собой, а начать разговор можно с готового вопроса.

- **Выгрузка — только своя.** `GET /chat/sessions/{id}/export` отдаёт диалог
  владельцу сессии; чужая сессия — 403. Форматов два: `md` (транскрипт для
  чтения) и `json` (те же данные, что и `GET /chat/sessions/{id}`).
- **Текст сообщений не экранируется.** Иначе в выгрузке ломались бы блоки
  кода и спецсимволы, а транскрипт перестал бы быть читаемым.
- **Имя файла — latin-1.** Заголовки HTTP ограничены latin-1, поэтому
  кириллическое имя передаётся в `filename*` (RFC 6266), а в `filename`
  кладётся ASCII-вариант.
- **Шаблон подставляется, но не отправляется.** Чип с шаблоном только
  наполняет поле ввода: автоотправка лишила бы ученика права решить, что
  спрашивать. Шаблоны подбираются по уровню помощи: базовому уровню не
  предлагается «полное решение».
- **Личные настройки — закрытый список.** В `users.settings` пишутся только
  известные ключи (`prompt_template`, `snippets`); произвольные данные клиент
  записать не может. Настройки дополняются, а не заменяются, чтобы клиент
  менял одну настройку, не присылая весь объект.
- **Шаблон хранится в профиле, а не в сессии.** Выбор шаблона — личная
  настройка ученика, а не свойство диалога: он одинаков для всех чатов.

### 11.39. Код между чатом и песочницей (S43-005)

Код, который ассистент показал, можно запустить, а код из песочницы — можно
показать ассистенту.

- **Код ходит через слот в localStorage.** Песочница забирает переданный код
  один раз при открытии; отдельно хранится черновик ученика. Два слота
  разведены намеренно: переданный код не должен молча затирать черновик.
- **Чужой черновик не перезаписывается без подтверждения.** Если в песочнице
  уже есть код и он отличается от переданного, показывается вопрос
  «Заменить текущий?» с вариантами «Заменить» и «Оставить текущий».
- **Код уходит вложением, а не «решением задачи».** При переходе из
  песочницы в чат код подставляется в поле ввода блоком кода — как вложение
  в сообщение, а не как ответ на задачу.
- **Автоотправки нет.** Ни в одну сторону: код ждёт в поле ввода, пока
  ученик не нажмёт «Отправить». Создание чата при переходе из песочницы —
  следствие явного действия ученика, а не отправка сообщения.
- **Код не покидает браузер.** Передача идёт между страницами одного
  приложения; ни в БД, ни в API код не попадает.

### 11.40. stdin, лимиты и разбор кода в песочнице (S44-001)

Песочница показывает ученику, что именно она принимает и как проверяет код.

- **stdin — явное поле.** Данные для `input()` вводятся под редактором и
  уходят в `POST /code/execute`. Интерактивной консоли нет: пустое поле
  означает, что ввод не передаётся.
- **Лимиты берутся из API.** `GET /code/limits` — единственный источник
  чисел; интерфейс не дублирует их и не хранит собственные копии.
- **Разбор — отдельное действие.** `POST /code/analyze` не запускает код.
  Замечания группируются по важности (`error`/`warning`/`info`), метрики
  показываются из `stats`, решение всегда за учеником.
- **Сбой загрузки лимитов не блокирует работу.** Блок сообщает об ошибке, но
  запуск и разбор остаются доступны.

### 11.41. История запусков в песочнице (S44-002)

История показывает, что ученик уже запускал, но не подменяет текущий запуск.

- **Только свои запуски.** Список приходит из `GET /code/history` и уже
  ограничен текущим пользователем; интерфейс не запрашивает чужие записи.
- **Запись раскрывается по клику.** В свёрнутом виде видны время, статус и
  длительность; код, вывод и ошибка показываются только в раскрытой записи.
- **«Запустить снова» не запускает код.** Кнопка возвращает код записи в
  редактор и очищает прошлый результат; запуск остаётся отдельным действием
  ученика.
- **История обновляется после запуска.** Новый результат появляется в списке
  сразу, без перезагрузки страницы.
- **Сбой истории не блокирует песочницу.** При ошибке сети карточка истории
  показывает сообщение и «Повторить»; редактор, запуск и разбор работают.

### 11.42. Файлы и сниппеты в песочнице (S44-003)

Код можно забрать с собой в файл и вернуть из файла, а часто используемые
заготовки — сохранить в личных настройках.

- **Скачивается текущий код редактора.** «Скачать .py» отдаёт браузеру
  `code.py`; сервер в этом не участвует, черновик и настройки не меняются.
- **Загрузка проверяется до замены кода.** Принимается только `.py` (регистр
  не важен), файл до 200 КБ (204 800 байт) и код до 20 000 символов. При
  отказе редактор остаётся прежним, причина показывается рядом с кнопками.
- **Загруженный файл не становится черновиком сам по себе.** Код появляется
  в редакторе, но в localStorage попадёт только после явного действия
  ученика — например, когда он начнёт править код (требование S44-004).
- **Сниппеты — личные и закрытые.** Список хранится в
  `users.settings.snippets`, а не в общей таблице; сервер принимает не больше
  20 сниппетов, уникальные id, название до 80 символов и код до 20 000
  символов. `null` очищает список, остальные настройки не затрагиваются.
- **Сниппет применяется в один клик, но не запускается.** «Применить»
  подставляет код и очищает прошлый результат; запуск остаётся отдельным
  действием ученика.
- **Удаление спрашивает подтверждение.** После подтверждения сниппет исчезает
  из профиля; ошибка сохранения или удаления показывается в карточке и не
  блокирует редактор.

### 11.43. Состояние редактора (S44-004)

Код переживает перезагрузку страницы, но остаётся личным и локальным: он не
уходит на сервер сверх обычного черновика задачи.

- **Контекст вместо одного общего ключа.** Песочница хранится в
  `ai-teacher.editor.code`, задача — в `ai-teacher.editor.task:<id>`. Код одной
  задачи не появляется в другой, а чужая песочница не подменяет задачу.
- **Запись живёт 30 дней.** Вместе с кодом хранится время сохранения;
  просроченная или повреждённая запись удаляется при чтении. Старый ключ
  `ai-teacher.code.draft` один раз переносится в новый формат, чтобы черновик
  не потерялся после обновления.
- **Локальная копия важнее серверной, если она новее.** При открытии задачи
  сравниваются время локального сохранения и `draft_updated_at`. Более новый
  локальный код восстанавливается, и интерфейс предупреждает, что он новее
  черновика на сервере. Если новее серверный черновик, показывается он.
- **Загруженный файл не сохраняется сам.** «Загрузить .py» меняет только
  редактор; в localStorage код попадает после явного редактирования. Если
  сохранённый черновик новее файла, замена требует подтверждения.
- **Очистка разделена.** «Очистить сохранённое» удаляет локальную копию, не
  стирая код из редактора. «Удалить черновик» очищает серверный черновик
  задачи. Явная отправка решения удаляет и серверный, и локальный черновик.

### 11.44. Смена пароля и версия refresh-токенов (S45-001)

Пароль меняется только с подтверждением текущего; успех отзывает чужие
сессии, но не выкидывает текущее устройство.

- **`token_version` — рубильник refresh-токенов.** Пара токенов содержит `tv`
  (версию пользователя); смена пароля увеличивает её. Refresh-токен с меньшим
  `tv` получает 401. Access-токены остаются короткоживущими и версию не
  проверяют (решение KI-027).
- **Проверка текущего пароля обязательна.** Неверный `current_password` — 400
  и никаких изменений: токен с чужого устройства не должен менять пароль.
- **Ответ содержит новую пару.** Успешная смена возвращает `access_token` и
  `refresh_token` с новой версией; фронтенд сохраняет их и перезагружает
  профиль. Без этого текущая сессия умерла бы вместе с отозванными.
- **Политика пароля:** `new_password` — от 8 символов и не длиннее 72 байт
  UTF-8 (ограничение bcrypt проверяется до хэширования). bcrypt считается
  в `run_in_threadpool`, чтобы не блокировать event loop.
- **Аудит:** факт смены пишется как `user.password_changed`.

### 11.45. Правка профиля и удаление аккаунта из UI (S45-002)

- **Правка — существующий `PATCH /auth/me`.** Уникальность e-mail/username
  проверяет сервер; UI показывает `detail` ошибки как есть, чтобы пользователь
  понял, что занято.
- **Письмо на старый адрес.** При реальной смене e-mail отправляется
  best-effort уведомление на прежний адрес; ошибка SMTP не ломает запрос
  (в лог — warning).
- **Удаление — только по паролю и с явным предупреждением.** Модальное окно
  повторяет текст `PRIVACY.md` о необратимости. Локальная сессия очищается
  **только после успешного** `DELETE /auth/me`: при неверном пароле аккаунт
  жив и разлогин был бы ложным.

### 11.46. Выгрузка своих данных (S45-003)

- **Только свои данные.** `GET /users/me/export` собирает профиль, прогресс,
  попытки, чаты, уведомления и достижения запрашивающего; чужие строки не
  попадают в выборки (фильтр по `user_id` на каждом запросе).
- **Служебное не выгружается.** Эмбеддинги сообщений, хэш пароля и внутренние
  поля остаются на сервере; `message_metadata` отдаётся в том виде, который
  пользователь видел в ответе.
- **Файл — вложение.** Ответ идёт с `Content-Disposition: attachment` и именем
  `ai-teacher-export-<дата>.json`; сервер файл не хранит. Каждая выгрузка —
  аудит `user.data_exported`.

### 11.47. Настройки уведомлений и языка (S45-004)

- **Закрытый список ключей.** В `users.settings` разрешены только
  `language`, `email_notifications`, `deadline_notifications`, `deadline_days`
  (плюс прежние `prompt_template`/`snippets`). Валидация — 422.
- **Отсутствие ключа = значение по умолчанию.** `language=ru`, оба
  уведомления включены, `deadline_days=3`; миграция существующих пользователей
  не нужна. `deadline_days` удерживается в 1…14.
- **Настройки уважают рассылки.** Выключенный `email_notifications` исключает
  письма о назначениях, `deadline_notifications` — напоминания, а
  `deadline_days` задаёт окно `sync_deadline_notifications`. Скрипт
  `notify_deadlines.py` использует те же правила.
- **Язык применяется сразу.** Переключатель в шапке вызывает
  `i18n.changeLanguage` и сохраняет выбор в профиле; при следующем входе
  язык профиля применяется после загрузки `GET /auth/me`.

### 11.48. Активные сессии и их отзыв (S45-005, закрывает KI-028)

- **Сессия = устройство.** `user_sessions` хранит `jti`, user-agent, IP и
  время; `jti` входит в обе части пары токенов и ротируется при refresh,
  поэтому старый refresh-токен одноразовый.
- **Точечный отзыв.** `DELETE /users/me/sessions/{id}` ставит `revoked_at`;
  refresh этого устройства получает 401. Чужая сессия — 404, текущая — 400
  (для неё есть выход из аккаунта).
- **«Выйти везде».** `POST /users/me/sessions/revoke-others` увеличивает
  `token_version`, отзывает все строки и возвращает текущему устройству новую
  пару — оно остаётся в системе. Действие — аудит `user.sessions_revoked`.
- **Совместимость деплоя.** Refresh-токены без `jti` (выданные раньше) не
  отклоняются: для них создаётся новая сессия. Так обновление не разлогинивает
  активных пользователей.
- **Приватность.** User-agent и IP видны только владельцу в его списке сессий;
  отдаются обрезанными (255/64 символа) и не попадают в логи аналитики.

### 11.49. Клиентский IP, доверенные прокси и лимиты (S34-003/004)

- **Единый резолвер.** IP клиента определяется только `client_ip(request)` из
  `app/core/ip_utils.py`; `rate_limiter` и `audit_service` используют его же.
  Свой разбор `X-Forwarded-For` в других местах не писать.
- **Доверенные прокси.** `TRUSTED_PROXIES` — список IP/CIDR. `X-Forwarded-For`
  учитывается, только если TCP-peer входит в список; заголовок разбирается
  справа налево, доверенные хопы пропускаются, первый недоверенный IP —
  клиент. Пустой список = доверяем только TCP-peer.
- **Лимиты.** `POST /auth/login` — 5/мин на IP, `POST /auth/refresh` — 30/мин
  на IP (отдельный ключ), общий — 300/мин на IP; `POST /code/execute` и
  `POST /tasks/{id}/check` — per-user (`is_user_limited`). Все — fail-open при
  недоступном Redis, 429 с `Retry-After` при превышении.
- **Refresh-токен — только в теле.** `POST /auth/refresh` принимает JSON
  `{refresh_token}`; query-параметр больше не поддерживается: токен не должен
  попадать в access-логи прокси. Клиент обязан обновить вызов (S34-002).
- **Неактивный пользователь.** `require_role` строится на
  `get_current_active_user`: деактивированный teacher/admin получает 401 даже
  с валидным токеном (S34-001).

### 11.50. Наблюдаемость, PII и лимиты ресурсов (S35)

- **Метрики — события.** HTTP/LLM/sandbox/rate-limit/retention пишутся в момент
  события (counters/histograms), а не gauge из памяти процесса: только так
  значения корректно складываются при `UVICORN_WORKERS=2` и
  `PROMETHEUS_MULTIPROC_DIR`. Gauges состояния (`db_pool_*`, `db_up`,
  `redis_up`) используют `livesum`/`max`/`min` осознанно.
- **`/metrics` — только внутренняя сеть.** nginx отдаёт 404; наружу не
  публиковать. Проверка после деплоя —
  `python scripts/monitoring/check_metrics.py --expect-workers 2`.
- **Алерты как код.** Правила — `deploy/monitoring/prometheus/rules/*.yml`,
  у каждого алерта `severity`, `summary`, `runbook_url` на
  `docs/MONITORING.md`. Любое изменение проходит `promtool check rules`
  (локально и в CI job **Monitoring config**).
- **Sentry без PII.** `send_default_pii=False` / `dataCollection` (frontend),
  тела запросов не отправляются; `before_send` вычищает email, username, IP,
  токены, код и промпты; в тексте маскируются email/IP. Не отключать фильтр
  ради «удобной отладки».
- **Логи без PII.** Не логировать токены, пароли, полные email, тексты кода и
  промптов сверх необходимого; email маскируется. Ротация — Docker `json-file`
  `10m × 3`; Loki retention 7 дней.
- **Лимиты ресурсов.** Prod-compose задаёт `mem_limit`/`cpus` для всех
  сервисов (app 2 ГБ, postgres 1 ГБ, redis 128 МБ). Мониторинг — опциональный
  профиль, его отсутствие не ломает прод.
- **SLO и runbook.** `docs/SLO.md` — SLI/SLO/error budget; `docs/MONITORING.md`
  — как поднять стек и что делать по каждому алерту.

### 11.51. Секреты из файлов и guardrails LLM (S38)

- **`*_FILE` приоритетнее ENV** (`config.py`): `SECRET_KEY_FILE`,
  `POSTGRES_PASSWORD_FILE`, `DEEPSEEK_API_KEY_FILE`, `SENTRY_DSN_FILE`,
  `SMTP_PASSWORD_FILE`. Ошибка чтения/пустой файл — фатальная при старте; не
  заменять на «тихий» fallback в ENV.
- **Docker secrets** — `deploy/docker-compose.secrets.example.yml`; файлы
  `secrets/` в `.gitignore`, права `0600`. В логи и Sentry секреты не попадают.
- **Системный промпт** всегда содержит блок «Безопасность и границы»
  (`guardrails.SECURITY_INSTRUCTIONS`); при изменении промптов поднимать
  версию в `versions.json`.
- **Вход ученика** проверяется `check_user_input` до сохранения/LLM:
  injection/токсичность/самоповреждение → `ValidationError` с безопасным
  сообщением; текст попытки не логируется. Не отключать
  `LLM_GUARDRAILS_ENABLED` в production.
- Полная модерация ответов для детей — `KI-036`; новые правила контента
  фиксировать в `PRIVACY.md`/`ASVS_L1.md`.

### 11.52. Лимиты тела, загрузок и таймауты (S39)

- **Тело запроса:** Caddy `request_body { max_size 10MB }`, nginx
  `client_max_body_size 10m`. Не увеличивать без пересмотра памяти/диска.
- **Импорт задач:** `MAX_UPLOAD_BYTES` (10 МБ) проверяется в приложении
  (`UploadFile.size` и чтение `limit+1`); JSON/YAML/UTF-8, иначе 413/415.
  Полагаться только на прокси нельзя — приложение должно отказывать само.
- **Таймауты upstream:** Caddy `dial 5s`, `response_header 60s`, `read 600s`,
  `flush_interval -1` (LLM-стрим); nginx `proxy_connect_timeout 5s`,
  `proxy_send_timeout 60s`, `proxy_read_timeout 3600s` (WS). Песочница —
  `EXECUTOR_TIMEOUT`. Значения синхронизировать с `docs/PERFORMANCE.md`.
- **Perf-регресс:** nightly запускает health/tasks/submit; p95 > бюджета или
  +20% к измеренному baseline — красный job. Обновлять baseline только после
  осознанного изменения производительности.

## 12. Отчёты по шагам спринта

Каждый шаг спринта документируется отдельным файлом:

```
docs/reports/sprint-N/STEP-MM_<ТЕМА>.md
```

Обязательные разделы:

1. **Шапка:** дата, спринт, задача (`S-N-NNN`), статус.
2. **Что сделано** — нумерованный список.
3. **Проверки** — таблица "проверка → команда → результат".
4. **Файлы** — что создано/изменено.
5. **Проблемы и отклонения** — со ссылками `KI-NNN`.
6. **Обоснование решений** — варианты, что выбрали.
7. **Что дальше** — следующий шаг.
