## 0. Цели этапа

v0.2.0 сделал продукт пригодным для класса. v0.3.0 делает его **эксплуатируемым
и масштабируемым**: зелёный CI как обязательное условие мержа, современные
зависимости, предсказуемая песочница под нагрузкой, наблюдаемость, приватность
и закрытие UX-остатков.

| Направление | Что должно появиться к v0.3.0 |
|-------------|-------------------------------|
| Процесс | CI снова запускает job'ы и блокирует мерж; релиз — одна кнопка/команда |
| Зависимости | `fastapi` 0.162+ / `starlette` 1.x (KI-015), `pytest` 9.x (KI-016), 0 accepted-vuln без обоснования |
| Производительность | submit 5 RPS, p95 ≤ 2 с (KI-022) — батчинг кейсов + пул раннеров |
| Изоляция | песочница в отдельном контейнере (runner), non-root, без сети, read-only FS |
| Эксплуатация | `/metrics`, request-id, liveness/readiness, audit log действий teacher/admin |
| Данные | экспорт CSV/JSON, retention-политика, удаление аккаунта, заметка о ПДн |
| Продукт | поиск по чату в UI, массовые назначения, журнал оценок, email-уведомления (опц.) |
| UX | карточный вид таблиц, 100% локализация, авто-проверка контраста и a11y |

**Принципы этапа:**

1. **Сначала процесс, потом риск.** Спринт 21 возвращает CI — только после этого
   начинаются мажорные апгрейды (22) и изменения песочницы (23–24).
2. **Апгрейд без контрактных тестов запрещён.** Перед `fastapi`/`starlette`
   фиксируем OpenAPI-снапшот и ответы ключевых эндпоинтов (S22-001).
3. **Производительность измеряется, а не обещается.** Любая оптимизация submit
   подтверждается `scripts/load_test.py` и цифрами в отчёте.
4. **Обратная совместимость API v1.** Новые поля — аддитивно; breaking changes —
   только через `/api/v2` и отдельное решение.
5. **Приватность — часть DoD.** Данные учеников: минимум PII, retention, экспорт
   и удаление по запросу.

## Что не входит в этап

| Тема | Почему |
|------|--------|
| Мобильные приложения (iOS/Android) | отдельный продукт; веб адаптивен |
| Платежи/подписки | вне образовательной модели этапа |
| Мульти-тенантность и SSO | нужны организационные требования, не заявлены |
| Kubernetes/автомасштабирование | текущему масштабу хватает одного compose-стека; вернуться при 100+ RPS |
| Переход на другой LLM-провайдер | провайдер абстрагирован, менять причин нет |
| Реальный email-домен и доставляемость | фича за флагом; провайдер SMTP — решение эксплуатации |

## Риски этапа

| Риск | Влияние | Смягчение |
|------|---------|-----------|
| GitHub Actions не восстанавливается (биллинг) | блокирует required checks всех спринтов | self-hosted runner или GitLab-зеркало; локальные гейты + release скрипт; спринт 21 — приоритет |
| `fastapi`/`starlette` 1.x ломает поведение middleware/headers | нестабильный API | контрактные тесты (S22-001), апгрейд одним PR, canary на e2e |
| Пул/батч песочницы теряет изоляцию между кейсами | критично для безопасности | отдельный процесс/контейнер на задачу, тесты утечки состояния, лимиты |
| Контейнер-раннер недоступен на Windows-разработке | срыв S24 | fallback native + Job Object; контейнерный режим — опция |
| Метрики/аудит растят нагрузку на БД | деградация | батчинг, async-запись, retention, лимиты кардинальности |
| Приватность: удаление аккаунта задевает связанные сущности | потеря данных/ошибки | анонимизация вместо каскадного удаления, тесты, dry-run |
| Рост объёма LLM-вызовов (backfill, генерация) | стоимость | лимиты, квоты, провайдер метрик S12-003 |

## Как начинать спринт

1. Ветка `sprint/NN-<slug>` (см. RULES §2.1).
2. Прочитать раздел спринта, уточнить зависимости; для 21 — доступ к GitHub billing/runner.

4. Отчёт `docs/reports/sprint-NN/SPRINT-NN.md` + обновление журналов.
5. PR в `main`, зелёный CI, мерж.

в онбординг.
